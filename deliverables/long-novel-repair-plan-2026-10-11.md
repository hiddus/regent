# 长篇小说生成修复计划

日期：2026-10-11。依据：同日服务器失败复盘与 b0ce 导出。本文是实施计划，未表示修复已完成或服务器已通过。

状态：两轮评审后定稿，可进入实施。实施与验收以本文为准，冲突时以章节内的具体规定为准，修订记录只作说明。

## 目标与范围

第一轮目标：消除章内写穿、事件重演、状态污染和带硬矛盾入正史，能在干净分支自动完成三章并留下可核查证据。

约束：保留现有导演、执笔、场记、审校和责编；不新增模型角色，不增加正常成功路径的默认模型调用。允许在现有调用中扩展结构化输出，结构化输出解析失败计入失败路径。实际失败重试成本单独统计，不能以关闭硬门控制成本。

调用基线以服务器当前版本为准，即 `eba8990` 加两处热修。这一版已经包含角色自审：分场、执笔、场记、整章审校。成本分两种口径，不得混用：

- 正常路径调用结构：所有检查一次通过时，每章、每场按阶段发生的模型调用。用离线全通过桩模型在同一状态机上计数，基线版本用同样方法测得。新版本各阶段调用数不得高于基线，条件触发的自审在全通过路径上应为0次。
- 完整尝试成本：真实运行的总调用、重试次数与费用。b0ce 两章的63/70次是含失败重试的完整尝试（第2章最终失败），只作对照参考，不是正常路径的调用上限。

b0ce 中12次角色自审有11次判不通过，多数是摘录换行、标点差异。本轮须决定自审的去留与触发条件（见工作包4）。

范围只覆盖产品主链 `director_script_scene`（`directing_script_loop` + `chapter_review`）。协议 X 实验链 `experiments/scene_exec` 不在本轮；新增的纯程序检查须放在 domain 层，供两条链共用，避免复制一套。

本轮不是长篇能力认证。长期召回、故事段、钩子、文学编辑与节奏控制列入后续里程碑。保留已有工作区修改，不覆盖历史证据，不将有矛盾旧章直接当新基线。

## 工作包1：先堵污染入口，并修复回退

改动位置：application/directing_script_loop.py、chapter_review.py、chapter_accept.py、generation.py；domain/prose_front_gates.py、repair_locate.py、script_protocol.py。

### 1.1 问题协议

统一字段：issue_id、code、severity、origin、origin_scene_id、affected_scene_ids、evidence_spans、source_hash、status、verify_rule。origin 记录提出者：分场自审、场记、审校或程序检查。

状态为 OPEN / EVIDENCE_DEFECT / RESOLVED / WITHDRAWN：
- RESOLVED 必须记录复验版本和证据。
- WITHDRAWN 只用于证据复核中被提出方撤回的问题，须保留复核记录，并计入误报。
- EVIDENCE_DEFECT 为待复核状态，视同未结问题，不能入正史。

将严重性与递延标签分离。真实物件/资源/时序冲突、一次性事件重演、场景越界均为硬问题；文风建议、可接受省略可以为软问题。未分类的连续性问题不得自动降软，应通过现有审核明确分类。

移除 [gate_debt:cont] 一概可 coerce 的规则，以及纯递延问题修满后强制通过的兜底（`chapter_review._only_deferred_issues` 与 `coerced_deferred_issues`、`coerced_after_creative` 等路径）。递延仅允许暂存草稿，不允许写入后场正式入口或正史。b0ce 第1章即带着「滴答声骤然停了 / 从读取结束起就没停过」的递延矛盾入了正史。

审校硬问题必须带可程序核对的正文范围（当前正文中的逐字片段，或台账字段）。审校同时拿到台账，能区分合法重读和再次发现：b0ce 第2章第三轮把“重读笔记”判为冲突，属于误报。摘录不在当前正文、也对不上台账的硬问题，不直接触发重写，也不自动关闭或降软，按下列有界路径处理：

1. 程序把该问题置为 EVIDENCE_DEFECT，章节进入证据复核状态，正文、台账与已接受场次保持不变。
2. 由程序触发一次审校复核调用，输入为当前正文、台账和证据缺陷清单。复核须对每条给出可接地证据，或明确撤回。
3. 该调用计入本章失败路径调用预算，不消耗单场重写、章节修复或分场返工额度。同一轮审校最多复核一次，复核结果不能再次进入复核。
4. 补出有效证据的转为 OPEN，走正常修复路径；撤回的转为 WITHDRAWN；仍无法接地的结构化停机，输出问题、缺失证据与正文版本，禁止入正史。
5. 复核中新提出的硬问题同样须接地，不接地的直接停机，不再开新一轮复核。

### 1.2 最终接纳与正史硬门

在 finalize_chapter_acceptance 及 CANON 提交前复用同一确定性校验：没有未结硬问题；正文版本与场审/证据匹配；接受的 take 有效；台账出口来自已通过场次。review.passed 与 creative_accept 都不能单独替代该校验。

失败时保存结构化原因，不写正史/正式记忆；草稿与审计记录保留。

### 1.3 统一回退

固定保存 chapter_entry_state 与每场接受前快照。计划层回退恢复本章入口；第 i 场重拍恢复其入口并使第 i 场及后场的状态增量、正文接纳、摘要、证据和审核通过标记失效。

已确认的现有缺陷：`ASSEMBLE_CHAPTER` 把草稿出口写进 `production["working_state"]`，`_rewind_script_to_compile` 不重置它，`COMPILE_SCENES` 又优先用它作本章入口。审校打回重分场后，新计划会从失败稿的出口开始。修复后入口只能来自 chapter_entry_state。

保留现有上限：单场重写、章节修复与分场返工（2次）。更严的门不能变成无限重试。达到上限时停机，并输出结构化原因：未结问题、来源场、最后一次快照。

区分“当前章违背前章”与“前章自身矛盾”。前者修当前最早故障场，后者隔离前章及派生链。无法局部定位的结构问题回分场，不默认改最后一场。

验收：用含硬债务、创作通过、修满等组合证明全部拒绝入正史；证明回 COMPILE 后入口恢复而非继承失败出口；恢复/重试不复用失效审核。

## 工作包2：将 working_state 改为固定台账

改动位置：application/directing_contracts.py、directing_script_loop.py；domain/scene_card.py、script_protocol.py、chapter_handoff.py。建议新增纯程序 domain/continuity_ledger.py，不新增模型角色。

### 2.1 数据模型

首轮只落地 b0ce 已经出错的部分：Prop（位置、持有人、固定属性、分区文字、生命周期、读取状态）、Resource（亲忆这类消耗）、带作用域的一次性事件（见下），以及人物位置与时间标记。

“一次性”只在作用域内成立，不做全局判重。作用域键由程序生成，模型不能自填：

| 事件 | 作用域键 | 判重规则 |
|---|---|---|
| 能力读取 | 物件ID + 读取类型 | 按 Rule 判定；“读过的物不能再读”只限能力读取，Rule 明文例外放行 |
| 普通阅读/查看 | 物件ID + 分区 | 可重复，不扣资源；同一分区文字不得变化 |
| 首次发现 | 人物ID + 物件ID | 只发生一次；之后只能是再次查看 |
| 损坏/销毁 | 物件ID | 不可逆；维修须声明并有正文证据，生命周期回到可用后再按新状态判定 |
| 资源消耗 | 资源ID + 条目 | 同一条目只扣一次，须有 cause_event_id |
| 离开某地 | 人物ID + 地点ID + 访问轮次 | 同一轮次只离开一次；再次进入时程序开启新轮次 |Rule 只做作品已明文写出的能力规则登记，并与 Delta 对照，例如“每读一次失去一段记忆”“读过的物不能再读”“怀表本体拒绝读取”。通用规则引擎、容器/部件层级推理和人物已知事实推理放到后续里程碑，避免第一轮因模型过大无法落地。下列为目标模型，首轮按上述范围实现。

- Entity：entity_id、规范名、别名、类型、容器/部件关系。
- Prop：固定属性、分区文字内容、位置、持有人、生命周期、读取类型及状态。
- Resource：resource_id、已消耗条目、cause_event_id；记忆同义名称指向同一ID。
- Actor/Scene：人物位置、在场者、时间标记、已知事实。
- Rule：前置条件、允许动作、消耗、一次性限制、明确例外。
- Delta：对象ID、操作、字段、before/after、事件ID、正文摘录及范围、scene_id、prose_hash。

首次出现的物件允许提议注册，程序分配/确认稳定ID后再引用。unknown 保留未知，不允许猜测补齐；不得将不可逆状态改回 unknown。

人物/店铺身份同步规范化：开篇锁定ID，大纲、正文和长期承诺通过显式别名映射引用。不能按相似名字猜测自动合并不同角色。

b0ce 的漂移源头在大纲节点：`target_node` 写的是沈知时、沈望舒、林晚棠、时光修理铺，世界书与正文用的是沈寻、沈望岳、纪云岫、拾光钟表行，长期记忆里还留着旧名承诺。修复点是锁定世界书时生成映射，并在大纲节点和承诺进入导演、执笔、审校之前完成替换。不能只靠审校侧现有的 `soft-outline` 降软。

### 2.2 更新规则

既有场记一次调用输出实际事件及台账增量。程序验证字段、ID、前值、正文接地、版本、能力代价和生命周期；全部通过后应用增量并保存快照。

不能用自由文本 state_changes 的 update 作为正式入口状态。旧自由文本只保留诊断用途，所有正式消费端统一读同一台账。

区分 read_text/read_memory、发现/再次查看、损坏/不可使用/销毁。固定铭文允许被引用；不同页/补注区可新增内容，同一区文字不得无证据覆盖。

验收：拦截已碎齿轮再读、同一物件第二次能力读取、补注改字、颜色变更、重复记忆扣除、“免费读取却扣资源”、同一访问轮次内两次离店；允许重读笔记、声明并证明的维修、人物返回后再次离开、未确认字段继续 unknown。

### 2.3 旧数据兼容

兼容分两类处理，不得混为“旧作品走旧代码”：

- 新数据协议：固定台账、作用域事件、场记结构化增量、执笔白名单。用协议版本钉在作品上，只对新建作品生效。不将旧自由状态自动升级为高可信台账。旧作品若要切换，须先建可核查的台账基线，缺项时拒绝切换并列出缺项。
- 安全修复：覆盖新旧两条链路，旧作品同样生效。范围包括：取消真实硬矛盾与递延连续性问题的强制通过（1.1），最终接纳与正史提交校验（1.2，旧链路无台账时只校验未结硬问题、take 有效性与版本一致），回退入口恢复（1.3），以及正史去重与提交幂等（工作包4）。

旧作品不强制迁移，也不自动暂停；但遇到原本会被强制通过的硬矛盾时，改为结构化停机，不入正史。此次服务器重跑用新建作品，避免额外引入迁移模型调用。

## 工作包3：场景边界及执笔上下文

改动位置：domain/script_events.py、scene_card.py；application/directing_contracts.py、directing_script_loop.py、generation.py。可新增纯程序 scene_boundary.py、prose_overlap.py。

### 3.1 分场前检

每场明确 occurrence/consequence/reference、允许变化、保留给后场的事件、入口与出口。按场序模拟计划增量，检查同对象一次性事件、资源因果关系、能力规则和位置衔接。

不同事件编号不能绕过同资源/对象约束。允许新一轮事件必须满足规则，不以 new_reason 任意文本直接豁免。

### 3.2 正文后检

场记在现有调用里报告实际事件、模态（发生/回忆/计划/否定）及证据。事件编号必须取自本章 `script_events`，并另列“正文出现但清单中没有”的重大变化。程序对照责任场和台账；第一场兑现了排在后场的 occurrence（如齿轮读取/碎裂、离店）时立即拒绝接纳，并在重写指令中指明越界的事件和正文范围。

程序校验基于模型提取，不能宣称识别所有语义重演。用增量和实际事件互相核对，对无事件归属的重大状态变化要求解释/修正；新增背景细节不必全部禁止。

### 3.3 文本重复

WRITE 后、正式接受前与前章及已接受前场比较长连续复用和近似段落。返回新旧正文范围与场号，区分引用、固定铭文、短对白，阈值用正常/失败样本校准。

### 3.4 writer 白名单

执笔只读本场卡、相关台账、人物动机、必要记忆、前场/前章最后少量句子及本场修订意见。全书目标可作方向提示，后场重大事件不得混为本场要求。

从实际 payload 移除 recent_chapters.content、大段 previous_handoff、整章旧稿及其他嵌套全文入口。程序去重和整章审校仍可读取全文。设置确定性的上下文字数预算，不只是删一处参数。

验收：本次第一场在接纳前被拦；实际 writer payload 无隐藏前章全文；245字照抄被识别；引用和合法重读不误判为再次发生。

## 工作包4：修订复验、证据及去重

改动位置：directing_script_loop.py、chapter_review.py、chapter_accept.py、generation.py、chapter_handoff.py；按溯源结果决定是否增加数据库约束和迁移。

- 自审结果绑定 plan_hash/prose_hash/audit_hash，不以“场号已审过”代表新稿已通过。b0ce 第2章的分场自审指出“拉灭灯绳又打开”不是前章事实，并标了涉及前章；改后的计划仍保留这句，却因第二版不再自审而放行。
- 自审意见分两类输出，`RoleSelfReview` 相应扩展：
  - 可程序检查的结构化约束：字段缺失、事件归属到哪一场、某段文字须出现或不得出现、台账字段取值。程序预检逐条复验，通过即关闭，不通过即为硬问题。
  - 语义问题：如“这句虚构了前章事实”。写成问题协议里的 OPEN 问题（origin=分场自审，标注是否涉及前章），不能因为程序预检通过而关闭。由下游既有的场记（场级）或整章审校在其现有调用中逐条给出结论：带证据关闭，或保持未结。仍未结时不能接纳，涉及前章的按 1.3 隔离处理。
  - 同一意见同时给出文字约束和语义描述时，两者都要满足：文字约束通过只说明原句已删，不说明改写后的表述成立。
- 自审去留：摘录逐字、换行、标点和已有程序门可查的项目一律改由程序检查，不再占用自审的唯一一次修改。执笔和场记的自审改为条件触发：只在程序检查报出越界、照抄或台账冲突时，由同一角色带着具体证据复核一次。分场自审保留一次。验收按“目标与范围”中的两种成本口径分别报告。
- 摘录格式用程序接地及原文范围定位，允许安全的空白/标点规范化，不抹去数字、否定等事实差异。
- 已识别语义问题在下游既有场记/审校调用中复验；不关闭问题就不能接纳。无需每次新增自审调用。

## 工作包5：测试、发布与三章重跑

### 离线

2. 保留旧失败分支，在干净测试分支生成第1–3章；不沿用矛盾第1章。

### 回滚

保留部署版本可回滚。回滚针对新数据协议：新协议异常时，新建作品暂停正式续写，保留草稿与证据，不静默改回自由状态。协议版本不兼容时显式拒绝混用。

2.3 列出的安全修复不在回滚范围内。任何回滚版本都不得重新启用已确认的错误放行机制，新旧作品都一样。若必须回退到不含安全修复的代码，暂停所有作品的正式续写，而不是继续生成。
