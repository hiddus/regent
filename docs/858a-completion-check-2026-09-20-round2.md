## C1 · P1：摘要滞后判定仍是措辞判断与字符串不等比较

位置：`core/src/regent/novel/domain/scene_card.py:341–356`。

当前实现有两条不可靠的放行路径：

1. 命中“入场状态仍…”和“上场结尾已…”就返回 True，即使完全没有来源数据。
2. entry_summary 与 prior_scene_ending 去掉部分符号后只要不相等，就可返回 True。

实际 entry_summary 通常包括“上场结尾：”标签与“累计状态”字段，prior_scene_ending 则只是前场正文。即使二者事实完全一致，字符串通常也不相等，因此“不等”不能证明哪个状态过时，更不能证明本场没有真实矛盾。

### 本轮完整审核反例

已核状态：钥匙在甲手中。前场结尾：甲仍拿着钥匙。入口摘要也表明甲持有钥匙。本场无交接却变到乙手中。

审核问题改写为：

> 入场状态记录钥匙在甲手中；上场结尾描写甲仍拿着钥匙，本场却无交接变到乙手中。

设置 continuity_ok=False，调用完整 evaluate_scene_audit，实际 **blocking=False**。这与上一轮被拒绝的“也确认”样例是同一事实，只是用词不同。

另外，不提供任何来源，单独传“入场状态仍留锁死，上场结尾已写铁链落地”，is_entry_vs_ending_state_lag 仍返回 True。新增 test_r1_proven_lag_still_softable 将这种结果写为期望；该测试验证的是文案匹配，并没有验证“已证明”。

### 关闭条件

- 没有可核对来源时不授予滞后例外。
- 不用全文字符串不等作为事实冲突/滞后的证据。
- 对同一实体属性比较入口值、前场已接受正文的变化及来源版本；无法确定时保留阻断或明确要求重新核验。
- 加入同一真实矛盾的多种措辞，以及“摘要带标签/累计状态但事实一致”的完整审核反例。

## C2 · P1：定位只核验部分引文，且允许无关问题改变修订目标

位置：`core/src/regent/novel/application/directing_script_loop.py:301`，及 `_begin_located_scene_repair` 的模型条目合并。

`_verify_model_location` 对每个场景使用 any(evidence_grounded(...))：只要一条引文存在，就接受该条目的全部引文。随后合并逻辑只避免覆盖已定位的同 code 问题，没有要求模型条目必须对应某个尚未定位的 hard fail。

### 本轮反例

- 待修问题为 `[continuity] 乙的钥匙来源无法解释`，没有可检索摘录。
- 模型给 s0 和正确整章 hash，同时提供 s0 的真实长句及“此处完全虚构且不存在的证据”。
- 模型 code 为 unrelated，message 为“与原核验无关的问题”。

结果：

```text
_verify_model_location -> ('s0',)
_begin_located_scene_repair -> phase=WRITE_SCENE, scene_index=0
```

也就是说，模型只需带一条真实正文，就能把无关修订目标和虚构证据带进票据，截断并重写首场。合法 ID 和正确 hash 是必要条件，但不足以证明问题相关性。

### 关闭条件

- 每条将进入修订票据的引文，都必须归属至少一个所声明的场景；每个场景也必须有相应证据。不应要求跨场问题的所有引文都同时存在于每个场景。
- 通过稳定 issue_id 或明确映射，将模型定位绑定到当前未解决 hard fail；未知/无关条目不能改变修订目标。
- 缺失节拍采用 beat_id→scene_id 映射，不能只从 message 中模糊寻找片段。
- 测试真假引文混合、真实引文但无关问题、跨场多引文、同类多个独立问题，确认既不误接受也不漏修。
