## 结论

**上一轮多数具体缺陷已修，但仍不能认定开发全部完成。** 当前可以确认“新增修复已通过本地回归与前端构建”，不能确认“质量闭环已完成”或“可以稳定自主连续创作”。

本轮发现五项仍需处理的代码/Prompt 契约问题：连续性误放行仍有另一入口；回退时上下文版本不一致；修订指纹取错正文；模型定位证据未接地；新运行调用键版本在 ASSEMBLE 重建时丢失。前四项已有本轮最小探测结果，最后一项由重建代码及版本解析探测共同支持。

代码质量较前轮明显提升：位置越界开始明确拒绝、去重与事实纠错分开、恢复错误可见、连续授权接入界面、后继创建使用作品锁与保存点。主要短板转为跨模块数据契约和测试覆盖。

Prompt 的字面指令已改善，但输入仍可能相互矛盾、缺少场景边界或未经证据核验。当前问题不能靠继续增加“必须、禁止”解决；应先保证输入事实、场景、版本和验收对象一致。

## 剩余问题（按优先级）

### R1 · P1：连续性门仍按两个关键词放行真实矛盾

位置：`core/src/regent/novel/domain/scene_card.py`，`is_entry_vs_ending_state_lag` 与 `continuity_should_block`，约 265–293 行。

`is_entry_vs_ending_state_lag` 仅检查问题文字同时包含“入场状态”“上场结尾”。`continuity_should_block` 对全部符合该文字规则的问题直接返回 False，不核对哪个状态过时、前场证据是什么。

本轮调用完整 `evaluate_scene_audit`：已知状态为钥匙在甲手中，审校报告“入场状态确认钥匙在甲手中，上场结尾也确认在甲手中，但本场无交接就变到乙手中”，continuity_ok=False、无其他 hard_fails，结果 **blocking=False**。

这不是前轮已修反例的重复报告，而是另一个生效入口。真实冲突被归到 continuity_issues 是合理 schema 用法，不能要求模型再重复填 hard_fails 才能避免误放。

修复与验收：摘要滞后例外必须比较带来源的入口状态与前场正文；无法证明滞后就保留阻断。用完整审核函数测试“真实滞后可处理、真实矛盾不能放行”，不要仅测 soft 辅助函数。

### R2 · P1：回退场景后仍携带未来场景摘要

位置：`repair_locate.py` 的 `apply_repair_target_to_script_state`；`directing_script_loop.py` WRITE_SCENE 的 entry_summary/working_state payload。

回退助手截断 scene_texts、恢复 scene_state_trail 与 working_state，却没有同步重建 working_summary。WRITE_SCENE 同时发送恢复后的 working_state 和旧 working_summary；后者来自失败章最后场的结尾及累计状态。

本轮复现：从 s1 回退 s0 后，working_state 已恢复为 before，working_summary 仍为“STALE: end of s1”。因此模型会收到“从起点重写”以及“后续事件已经发生”的矛盾上下文。这会制造提前知道信息、重复动作或状态跳跃，属于直接影响 Prompt 输入质量的代码缺陷。

修复与验收：摘要纳入场景入口快照；回退 s0 清除后场摘要，回退中场从保留的前场正文与入口状态重建。核对真实 WRITE_SCENE 请求，而不仅检查 scene_index。

### R3 · P2：修订票据的基准 hash 不是实际正文 hash

位置：`repair_locate.py:144–200`，`directing_script_loop.py` 的修订无进展检查。

为统一重复检测的段落索引，`_chapter_from_scenes` 只保留长度至少 32 字的段落。`locate_fail_messages` 优先用这份过滤正文计算 content_hash，忽略传入的完整 chapter_content；后续无进展检查却对完整 take.content 计算 hash。

只要正文有一句短对白或短段落，两者就可能永久不同。实测混合长短段、全文未变时，票据 hash 与完整正文 hash 比较为 False。

影响：并非无限重试，外层次数上限仍在；但“正文未变且问题仍在”的提前止损分支会漏触发，正文版本也不能正确绑定。

修复与验收：检测投影和权威正文分开。段落匹配使用统一分段，版本 hash 始终取实际完整正文。加入短对白/长段混合正文未变化的完整修订检查反例。

### R4 · P1：合法场景 ID 仍可携带伪造证据触发截断重写

位置：`directing_script_loop.py:243–274` 的模型定位合并；`repair_locate.py` 的位置选择。

当前检查 ID 是否属于 cards，但没有验证 evidence_quotes 是否出现在所指 scene_text 中，也没有校验模型 content_hash 对应当前稿。模型定位条目被追加到确定性定位结果，而不是依据同一问题身份验证后补齐。

实测：原 hard fail 没有可检索位置，模型给合法 s0、引文“完全不存在的引文”，仍进入 **WRITE_SCENE**。如果原确定性映射在后场而模型误报首场，也可能不必要地提前截断。

修复与验收：程序生成/核对正文 hash，逐个校验引用与场景归属；只有确实对应待修问题的定位才能改变目标。缺失节拍没有原文证据时，使用场景卡 beat_id→scene_id 映射，而非允许任意猜测。增加合法 ID+伪引文、正确引文+错误场、过期 hash、冲突定位四类反例。

### R5 · P2：新运行的调用键版本在上下文重建后退回旧版

位置：`generation.py:886–950`、`executor.py:100`、`directing_calls.py:45–58`。

新运行/后继运行将 call_key_version=2 写入根上下文及 production。ASSEMBLE 重新赋值 generation_context 时，只通过 carry_over 保留执行器字段和少数纠错字段，不保留 call_key_version、production 或 continuation。之后 `_init_script_production` 又新建 production。

因此新运行进入 hydrate 时可能两处都找不到版本，按旧运行解析为 1。最小 carry_over→resolve 探测从版本 2 得到 1，完整重建代码确认没有额外保留路径。

该结论不表示已发生重复收费；具体问题是声明的新旧格式分流没有贯穿真实生命周期，continuation 的 source/policy 追踪信息也会丢失。

修复与验收：将运行身份及授权来源列为必须保留的字段，统一生产状态初始化规则。测试 start_run/ensure_next_run→ASSEMBLE→DIRECT→WRITE_SCENE；旧运行保持 1，新运行保持 2，并检查已有成功调用的复用。

## Prompt 质量评价

**任务表达已改善，输入与验收契约尚不合格。**

已确认改进：事实证据和重复摘录分开；system 与 payload 统一使用 expected_actions；明确多动作顺序、保留正确内容、输出完整本场正文；修订位置非法时不再默认首场。

仍需处理：

1. **输入一致性：**R2 导致同一请求同时包含旧摘要与恢复后状态，模型无从可靠判断优先级。
2. **位置可判断性：**REVIEW 要求返回“分场顺序的 failed_scene_index”，实际 payload 仍仅有 chapter、recent_chapters、target_node、canon，未提供实际分场边界。模型只能从文本自行猜分场，程序又可能信任有效范围内的猜测。
3. **正确事实来源：**ticket 将问题描述直接存为 forbidden_claims；测试中“钥匙应在小李手中”也进入该字段。它实际是目标约束而非禁止断言，命名语义仍混乱。应区分错误断言、正确状态及其已核来源。
4. **证据可信度：**R4 表明提供结构化字段不等于接地。程序必须验证模型引文，而不是提示里说“逐字”就信任。
5. **验收对应关系：**verify_repair_progress 主要按 code 和文本 ID 比较，不等于逐问题语义验证；问题文案变化不应自动记为解决。当前核验大门仍可拦错误，但票据指标不宜用于宣称纠错成功率。

建议发送“scene_id + 当前正文与版本 + 已核入口事实 + 相关前场结尾 + 逐问题修订目标”，审校使用同一场景边界。优先修输入和程序验收，不继续堆叠提示词。

## 连续创作和并发的剩余验收

连续授权入口已存在，不能再重复上一轮“没有入口”的结论。当前还需明确：

- `volume_scope=current` 使用运行时 total_volume_count 查卷尾，没有固定授权时的卷身份；卷尾没有已知 end_chapter_no 时不限制。应明确扩卷确认是否同时重新授权连续运行。
- `authorized` 与 `unbounded` 当前没有分别执行卷范围限制；budget_grant_note 是备注，不是可校验的总费用授权。
- 作品锁与保存点是正确改进，但新增 F5 测试仍为同 session 顺序两次调用，不是 PostgreSQL 双 Worker。作品策略 PUT 也未提供期望版本检查。
- 需要产品入口一次开启、关页三章、暂停/恢复、目标到齐停止、历史失败重生后继续、双 Worker 竞争与卷末确认的组合验收。

上述范围问题本轮未做生产复现，作为契约与发布验收缺口，不写成已发生的线上事故。
