# Regent 失败案例复盘：定义满分，执行敲边鼓

> 用途：作为「反面教材」给团队演示——定义和需求都没问题，项目却实际失败了。
> 核心论点：**graph 工程（多 Agent 编排 / 治理 / 评测框架）重要，但不能因此漏掉 Agent 的基本功。**
> 证据来源：仓库内 `Regent-PRD.md` / `Regent-Plan.md` / `Regent-Technical-Spec.md` / `Regent-Measurement-Decision-Framework.md`，以及 `code-regression-check-2026-08-02.md`、`delivery-pipeline-unblock-plan-2026-08-01.md`、`doc_impl_readme_conformance_check_2026-07-31.md` 三份诊断报告。
> 日期：2026-08-02

---

## 0. 一句话结论（demo 开场用）

定义、需求、技术规范本身质量极高，甚至可以当范本。但项目实际失败了——失败**不在"想错了什么"，而在"一直在做周边，最核心的那条线始终没打通"**。

大量精力投在了 graph / 多 Agent 编排 / 治理闸门 / 评测框架这些**高阶知识**上，却漏掉了 Agent 最该先会的**基本功**：一个能在约束下稳定交付、失败有明确出路的单 Agent 执行闭环。

这就是「敲边鼓」：鼓点密、架势足，但没敲在鼓心。

## 2. 实际错误原因归类

把表面症状归到根因，再对应到「漏掉的基本功」。

### 根因 A：基本功没打牢——单 Agent 执行闭环从没真正闭合 ⭐ 最核心

**现象**（来自交付管道解卡报告）：
- 管道卡死：创建后几小时没动静，反馈无效，补充方向无后续；
- 终端状态进不去：`GO` 状态机 `INVALID_STATE cannot mark FAILED_TERMINAL`；
- 事件没人消费：`DeliveryStateChanged` 发出后 handler 缺失 / outbox 幂等化抱团 → 事件无人处理；
- 队列饿死：单 worker 串行长 LLM 调用 → `PENDING` 积压 → 全体系卡死。

**漏掉的基本功（Agent 101）**：
1. **一个能跑起来的最小闭环**：用户提供 Goal → 5 分钟内出现可感知进展 → 成功 / 失败都有明确终态。这是最基础的东西，却长期不通。
2. **状态机卫生**：每个状态都必须有定义好的出口，**永远不能"悬停"**。可他们连 `FAILED → FAILED_TERMINAL` 都会抛 `INVALID_STATE`。
3. **持久化执行 / Outbox 纪律**：事件必须有人消费，毒事件必须进死信并清理；可他们发了事件却没 handler。
4. **背压与并发**：单 worker 串行跑长 LLM 调用，没有并发上限，队列饿死全体。

> 教训：**没有「能跑的最小闭环」，后面所有编排、治理、评测都是空中楼阁。**

---

### 根因 B：把「控制流」当成「能力」——伪验收代替真实行为

**现象**：计划里全是「✅ 控制流已实现 / 骨架已完成」，但真实状态是「完整真实实验窗口待 / 未开」「`pass_rate ≈ 0`」「在漏斗顶端堵塞时只能测出无效流量与僵尸 Goal」。

**漏掉的基本功：验收要按"真实外部行为"，不是"代码路径存在"。**
- PRD 自己写了「内部 smoke 不得满足产品价值 Gate」「禁止用源码字符串 / 类名存在代替行为验收」；
- 结果自己屡屡违反：用 `"decide_delivery_verdict(" in src` 这种源码字符串做断言、用 `delivery-review-v1` 魔法字符串兜底（见合规核对 §3-D/§3-E）。
- 这正是把 graph 工程的「门禁 / 闸门」概念形式化之后，**空洞化成了"开关变量已接上"**——闸门接上了，但门后根本没有能跑的东西。

> 教训：**「控制流已实现」≠「能力已具备」。没有端到端跑通的固定用例，所有 ✅ 都是伪证。**

---

### 根因 C：基本功没打牢之「工程卫生」——版本控制 / 测试 / 数据契约

**现象**：
- 未提交模块 `goal_runtime_plan.py` 被已改代码强依赖 → 干净 checkout 直接 `ImportError`（F-1）；
- `failure_lessons` 改 schema 不迁移，旧 lesson 被新读取方静默过滤掉，且丢的正是「从失败学习」的核心数据（F-2）；
- 26 个未跟踪文件里大量一次性 `ops/probe_*.py` 救火脚本（F-6）。

**漏掉的基本功**：
1. **提交卫生**：新模块和对应测试必须一起进版本控制；干净 checkout 必须能起服务（CI 冒烟）。
2. **数据契约演进**：字段变更要带迁移 / 兼容读取，不能靠「新读取方只认新字段」把旧数据静默丢掉——尤其这丢的还是学习闭环。
3. **救火 vs 根治**：用一次性脚本救火，是在掩盖根因，不是修复。

> 教训：**工程卫生是 Agent 系统的地基。地基裂了，上面再华丽的 graph 也会塌。**

---

### 根因 D：优先级倒置——先上高阶 graph，补了单 Agent 才该有的东西

**现象**：投入巨大在 MA-0…MA-6（多 Agent 评测 / 协作 / MAST）、GQ-0…GQ-5（生成策略实验）、CD-0…CD-12（对话式交付）、Impact Graph、AgentEnvelope、自适应组织……

**而当时的 PRD（2.0 基线，2026-08-10 已被定义 3.0 取代）明令**：
- 「多 Agent 不是默认架构，必须通过冻结实验验证净收益」；
- 「单 Agent champion 保持默认」；
- 「组织是执行手段，不是产品身份」。

> **口径更新（2026-08-10）**：上述三条已按 [`REGENT-DEFINITION-3.0`](docs/definitions/REGENT-DEFINITION-3.0.txt) 修订——净收益与冻结实验只决定**是否扩大现实生产权限或晋级生产默认策略**，不再作为沙箱候选拓扑的前置条件（ATTRIBUTE_2/4/6）。本节保留原文用于复盘当时的判断依据，不作为现行规范。

**漏掉的基本功：架构顺序。** 先有一个在约束下稳定交付的**单 Agent 内核**，再去谈编排、评测、自适应。他们把「graph 工程重要」理解成了「现在就做 graph 工程」，跳过了「先把一个 Agent 做对」。

> 教训：**graph 工程是"验证增益的手段"，不是产品本身。单 Agent 基线没闭环前，不该把投入重心压在自适应组织上。**
>
> 这条讲的是**投入顺序**，不是准入条件。按定义 3.0（2026-08-10），沙箱内的候选拓扑与组织试验默认开放；需要 Gate 的是把某种编成晋级为生产默认或让它继承不可逆现实权限。当年的错误是"重仓高阶 graph 而单 Agent 闭环没跑通"，不是"允许尝试组织演化"。

---

### 根因 E：元工作替代了真工作——用写文档 / 审计 / 决策记录安抚进度

**现象**：`docs/` 约 73 份文件，大量「对齐审计 / 差距重检 / 决策记录 / 修复计划」；同一类问题反复出诊断报告（`gap-recheck` 1/2/3、多次 `restoration-plan`）。

**漏掉的基本功：Done 的定义。** Done = **用户侧可验证的结果**，不是「又出了一份方案 / 审计」。当写文档的速度超过修代码的速度，就是敲边鼓的典型信号。

> 教训：**文档 / 审计 / 决策记录是手段，不是产出。用"我们在严谨地做事"覆盖"我们没做出东西"，是最隐蔽的失败。**

---

## 3. 为什么「定义没问题、要求没问题」还会失败（回应原话）

1. 定义 / 需求 / 规范的高质量，是**必要条件，不是充分条件**。它们把"该做什么"讲得极清楚，但没法（也不能）保证"做出来的东西是真的"。
2. 真正的断裂点在：**文档体系把"有控制流 / 有开关 / 有骨架"当成"已落地"，而真实验收所需的可运行证据长期缺失。**
3. 一句话总结：他们用**"治理的严密"覆盖了"交付的空虚"**——每一份文档都在说"我们在严谨地做事"，但管道已经 32 天没动过。

## 4. 给小伙伴的「正确搭 Agent」清单（从失败反推）

按 **基本功 → 进阶** 的顺序，这是 Regent 该有的优先级：

| 顺序 | 该先做（基本功） | Regent 实际（倒置） |
|---|---|---|
| 1 | 先让**一个单 Agent** 跑通最小闭环：Goal → 执行 → 可验证结果 → 明确终态 | 直接上多 Agent / Hive / 自适应组织 |
| 2 | 状态机先保证 **无悬停、可恢复、幂等** | 连 `FAILED → 终态` 都会 `INVALID_STATE` |
| 3 | 验收只认**真实外部行为**（跑通固定用例 + 真实 Observation） | 「控制流已实现」式伪验收、源码字符串断言 |
| 4 | 数据契约变更**必带迁移**；提交卫生要 CI 冒烟（干净 checkout 能起） | 未提交模块导致 `ImportError`；schema 不兼容静默丢数据 |
| 5 | Outbox / 事件**必须有消费方与死信**；背压有上限 | 事件无人消费；单 worker 串行拖死队列 |
| 6 | 高阶（graph / 多 Agent / 评测框架）是**验证增益的手段** | 在单 Agent 基线没闭环前，已重仓编排与评测 |
| 7 | Done = **用户可验证的结果**，不是又一份计划 / 审计 | `docs/` 73 份元文档 vs 卡死 32 天的管道 |

---

## 5. 一句话带走（demo 收尾）

> **Graph 工程重要，但 Agent 的"根"是一个能在约束下稳定交付、失败有明确出路的单 Agent 闭环。**
> Regent 把大量算力花在了描述"如何严谨"，却没把"如何跑起来"这件事本身做扎实——这就是最该被记住的反面教材。
