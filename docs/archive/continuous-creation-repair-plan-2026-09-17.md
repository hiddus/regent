# 连续创作阻塞复查与修复计划

日期：2026-09-17；状态：待实施提案。以当前工作树为依据，不替代 Novel-Engine-Plan.md。采纳后将任务与出口回填唯一执行计划。

## 1. 本轮结论及证据范围

当前问题不能简单归因于模型写作能力。至少存在三处已复现的状态衔接断点和一处后台调度饥饿；同时真实生成实验仍有场景核验失败。流程连续与内容连续须分开修复、联合验收。

本轮重新检查了已拆分的 works_*、directing_*、新 Worker 模式、前端和最近本地实验产物。此前建议中的模块拆分、服务模式隔离、editorial_repair 已有实现，不能再把“尚未拆模块”列为当前主因。

本轮执行：

- 定向测试：checkpoint replay、末节点/卷、D 批、纠错恢复 API、预算、追加额度、租约隔离，共 **52 passed、1 failed**。
- 在内存 SQLite 中用真实应用服务、假模型复现四个流程问题；没有连接生产、没有付费模型调用、没有修改业务代码。
- 阅读 9 月 16—17 日留在本地的 R3 和 serial_modular_x3 证据。文件更新时间不等于对应部署源码版本，历史失败不能直接证明最新补丁无效。
- 未拿到本次用户具体作品 ID 或线上状态，因此以下确定的是当前代码可复现问题，不能断言线上只由其中某一项引起。

## 2. 先明确“完整连续创作”的验收契约

开启作品级连续创作后，在已授权的章节/费用/卷范围内：

1. 关闭网页后，Worker 完成当前章并自动创建、推进下一章。
2. 用户暂停、预算不足、重大裁决、真实质量硬错误均可以暂停，但必须有准确原因和可执行恢复动作。
3. 暂停恢复不能重写已接受章节、重复扣费或跳过失败章节。
4. 下一章读取上一章最终接受的正文、事实、人物状态及未兑现承诺。
5. 卷末根据授权结束、扩卷，或显示真实可操作的确认；不得停成没有入口的待裁决。
6. 到达目标章数、预算上限或明确终局时正确停止，不无限开章。

现有 run.auto_advance 的实际用途主要是跳过章内检查点。它不等同于“作品级自动连续写章”。产品和数据模型应明确这两个控制项。

## 3. 已确认问题与修复设计

### C01 / P0：缺少章完成到下一章的后台衔接

**证据**

- works_runtime.advance_background_run 只查询已存在的 QUEUED/RUNNING/RETRYABLE_FAILED 章任务。
- works_volumes._after_chapter_completed 在非末节点直接返回，没有后继章任务创建。
- 前端 nextChapter 通过 POST /works/{id}/runs 开章；阅读底栏是用户点击“续写”。
- run_r3_three_chapters.py 的三章循环也逐章 POST /runs，因此它证明的是有人逐章驱动时能生成，不是后台自主连续运行。
- 本轮服务探测：RUNNING 作品、第一章 CANONIZED、auto_advance=True，执行成章收尾和后台 tick 后仍只有一个 run，tick 返回 None。

**修改**

新增作品/分支级 continuation policy，最少保存 enabled、目标章数或停止条件、允许的卷范围、费用授权引用与版本。不要把每章 auto_advance 偷换语义；旧作品不能因部署自动获得无限生成授权。

新增小型 continuation_service，集中实现 ensure_next_run(work, completed_run)：

- 确认前章是当前分支的权威接受版本；存在待处理早章纠错时先修前章。
- 检查作品暂停、预算、裁决、终局、授权范围和后继任务是否已经存在。
- 锁作品/分支的推进记录，复核后创建一次后继任务；数据库唯一约束兜底，竞争冲突返回已有任务，不制造第二次尝试。
- 本章完成事务中写持久化 continuation 请求或同等持久待办；不在该事务内发下一章模型调用。
- Worker 补偿扫描“已授权连续、上一章已接受、没有后继任务”的作品，复用同一 ensure_next_run。补偿不是另一套创建逻辑。

若用 Outbox 承载请求，必须补上 novel 模式事件订阅和领取范围；若采用小说专属待办，不让旧通用队列成为新耦合点。

**出口**：只发一次启动请求并关闭页面，后台连续完成三章；重复完成事件、Worker 重启和双 Worker 竞争都只创建一个下一章。目标章数到达后不再建任务。

### C02 / P0：恢复作品不能恢复终止失败的章任务

**证据**

- works_run_control.resume_work 允许 FAILED→RUNNING，但不改变章任务。
- Worker 不领取 TERMINAL_FAILED。
- start_run 又将 TERMINAL_FAILED 当作已有活动章节，拒绝开新章。
- 本轮复现：恢复后 work=RUNNING、run=TERMINAL_FAILED，后台 tick=None；再次开章得到 Conflict: a chapter is already active。
- 实际终止失败也可能留下原本 RUNNING 的作品。因此既要覆盖 FAILED 作品，也要覆盖 RUNNING+失败章的组合。

**修改**

将“恢复”做成按阻塞原因路由的用例，而不是只切 work.state：

| 原因 | 动作 |
|---|---|
| 用户主动暂停 | 原 checkpoint 继续 |
| 次数/金额不足 | 已有授权追加路径；不清零累计费用 |
| 网络、限流等暂时故障 | 同逻辑调用按重试/对账规则恢复 |
| 调用结果 UNKNOWN | 对账后决定，不重复调用 |
| 必需节拍未落地、场景真实矛盾 | 从失败场做有界修订/重规划，保留前面接受内容 |
| 用户显式要求整章重写 | 新 attempt，保留旧版本并计算后续失效范围 |
| 当前版本程序缺陷 | 保留证据，修复部署后恢复，不盲目重试三遍 |

ProductionStopped 不应仅凭异常类一律代表“永久不可恢复”。补充结构化 failure_code、recoverability、failed_phase、checkpoint_ref、recommended_action。硬门仍保持硬门，改变的是如何修复和恢复，不是失败后自动认定合格。

恢复事务必须确保确实存在可领取任务，或明确返回“仍等待授权/对账/裁决”。任何情况下不能仅显示 RUNNING 来宣告恢复成功。

**出口**：可恢复故障能从指定检查点继续；终止失败后按钮能执行有效动作；重复点击不叠 attempt；旧费用、已成功调用及已接受场景保留；失败章未修好不得跳到后章。

### C03 / P0：卷末“等待确认”与扩卷后的恢复没有闭合

**证据**

- _after_chapter_completed 已改为卷末不自动扩卷，记录 volume.expansion_pending，并设置 work=PENDING_DECISION。
- 这一路径没有创建普通 DecisionRequest；前端却将 PENDING_DECISION 投影为 open_decision。
- 当前 App.tsx 未找到调用扩卷和终局 resolve API 的专用操作，只监听 volume.expanded。
- expand_next_volume 写新节点、新卷、total_volume_count，但不解除作品的待裁决状态。
- 本轮服务探测：待裁决作品成功生成第二卷后，仍为 PENDING_DECISION，未生成章任务。
- expand API 接收 volume_no，却未把它用于服务条件；顺序重复请求可能按更新后的 total_volume_count 再扩下一卷。其幂等性需补齐。

**修改**

将扩卷确认纳入持久化决策，或明确建立专属扩卷待办；不要只写一条事件就期待普通裁决入口能处理。

用户确认后的用例应完整处理：校验待确认卷和作品版本→获取并持久化扩卷大纲→幂等提交卷/节点→清除对应 pending/ending 标记→恢复作品→按连续创作策略创建新卷首章。模型阶段在长事务之外，并验证返回时用户意图仍有效。

目标卷号作为幂等身份的一部分；重复确认返回同一卷，不再扩第三卷。扩卷前仍检查用户终局和费用授权，不能通过扩卷绕过“只写两卷”。

若产品允许预授权范围内自动扩卷，可在 continuation policy 明确开启；超出授权或重大剧情选择仍停下来。无需每章审批，也不能无授权无限扩卷。

**出口**：真实卷末生成→用户可见确认→重复点击仍只产生一卷→新卷首章自动起跑；达到终局则完本，不能继续建议下一卷。

### C04 / P1：候选窗口饥饿与任务定位不够精确

**证据**

works_runtime 先选 updated_at 最早的 16 个候选，随后在 Python 中检查前章屏障。被屏障挡住的记录没有离开前 16。即使第 17 个候选可运行，后续 tick 仍重复检查同一批。

本轮复现：作品 A 的第 1 章待裁决，后面 16 个任务排队；作品 B 的第 1 章可运行。连续两次 tick 返回 None，B 未被选择。

另有待加强边界：候选查询未显式限制 candidate.branch_id=work.branch_id；领取候选后按 chapter_no 再找当前分支最新 attempt，而非按领取到的 run_id 推进。存在历史分支/尝试时，需要防止领取对象和推进对象不一致。

**修改**

- 将可执行性屏障尽量下推 SQL NOT EXISTS；按当前分支和权威 attempt 限定候选。
- 应用层仍复核锁内条件；如需跳过候选，采用游标继续扫描，不能每次从同一 16 条重新开始。
- 调度器以明确 run_id 和版本推进，而非只传章节号。
- 采用作品间公平调度，避免单作品大量重演挤占其他作品；保留前章优先。
- 真实终止失败且没有合法替代版本的前章，也必须阻止后章；不能仅检查“在途状态”就放过内容缺口。

**出口**：大量阻塞任务下其他作品仍被及时领取；旧分支不抢占；领取与执行同一 run；双 Worker 不重复推进。

### C05 / P1：调用键变更导致旧检查点恢复兼容风险

**证据**

本轮唯一失败 test_command_and_logical_call_contract：期望旧键尾段 `:rep1:dec1`，当前输出 `:rep1:vrep0:dec1`。directing_calls 已把 chapter_validate_repairs 加入标识，这是避免章核验返工同键异参所必需；但对旧运行，默认 0 也改变原先调用身份。执行器身份仍为 director_script_scene@1，未发现针对旧键格式的版本分流。

这证明存在契约漂移，不等于已经确认某个线上作品重复扣费。不能只改测试预期使它变绿。

**修改**

- 增加持久化 call_key_version，新运行使用含 vrep 的新格式，旧运行明确保留旧格式。
- 新返工必须使用新逻辑身份，不能为了兼容复用不同请求的旧输出。
- 旧成功调用复用前校验请求/schema/config 摘要；冲突时保留诊断并执行显式迁移，不模糊匹配。
- 变更执行器/协议版本并保存源码指纹；只升级新运行或经过定义好的 checkpoint 迁移。

**出口**：升级前写到一半、已成功调用但未推进 checkpoint、UNKNOWN 对账和升级后章核验返工四类夹具，均不重复调用/计费，也不复用错误结果。

### C06 / P1：状态展示只看作品状态，掩盖“运行中但无任务”

**证据**

works_projection 对 RUNNING 固定显示“正在写下一章”，对 PENDING_DECISION 固定 open_decision，对 DONE 显示“本卷完成/下一卷”。但 RUNNING 可能仅剩 CANONIZED 或 TERMINAL_FAILED；待裁决可能没有裁决记录；DONE 在终局逻辑中可能已经代表全书结束。

**修改**

统一基于 work + 当前分支权威 run + continuation policy + pending decision + budget/call ledger 计算状态，输出 blocker_code、可执行动作、最近实际进展时间和下一步责任方。

区分：正在写、等待自动开章、等待手动续写、用户暂停、预算暂停、待对账、待裁决、修复失败章、已完本。动作必须与后端允许的用例一一对应。前端轮询/SSE 只显示、更新，不能承担连续开章职责。

增加补偿检查“work RUNNING 却无可执行任务”。明确已授权且只是遗漏开章时调用 C01；等待用户或真实硬错则提示原因，不盲目重新启动。

**出口**：所有暂停和失败都有真实有效的操作；刷新/关页不改变运行；完本不误报下一卷；服务端错误不能被统一吞成“还没开章”。

## 4. 章内和跨章内容稳定性：独立修复，不靠降低门槛

最近本地产物 serial_modular_x3/summary.json：目标三章，仅一章 completed，五次失败，82 次调用，4,054 字。失败记录主要是必需节拍证据不在正文、入场状态与正文矛盾、已经发生的动作再发生。

与此同时 R3 有三章 CANONIZED 的样本。因此准确结论是“可以在某些运行中生成三章，但未证明自动连续且稳定成功”，不是“绝对写不出三章”。

当前 scene_card 和 directing_script_loop 已加入入场状态/上场结尾滞后的特殊处理，历史样本应成为回放集。不能把以前失败当成当前已经复现；也不能靠匹配问题描述里出现“入场状态”“上场结尾”就认定是假错误。

建议 C07：

1. 分开存计划 entry/exit 与已接受的 actual_state；任何尚未写出的剧本事件不得成为正式入场状态。
2. 每场从固定入场快照修订；重写当前场时不能以该场上次失败产物的出口状态作为入口。
3. 状态变更携带实体、属性、旧值/新值、来源正文版本与证据位置；判断摘要滞后需要核对这些来源，不靠描述关键词降级。
4. 当前场硬失败只修当前场；需要改前场时明确回退依赖范围，不一律整章重来。必须保留失败原因和累计费用。
5. 成章后，最终正文、证据、记忆和承诺绑定同一版本；下一章只读取该版本，检查已兑现承诺是否仍 OPEN、旧尝试是否仍贡献过期事实。
6. 审核最新 R3 858a 记录中“沈知返/沈望舒”与“陈默/陈国栋”节点承诺混存的来源。可能是旧大纲残留，不应直接认定跨作品泄露；应核对 goal/path/bible/canon 版本，清理失效计划并重建受影响投影。

验收采用真实失败回放和三章因果链：第一章留下明确承诺，第二章引用正确事实，第三章兑现并关闭对应承诺；同时注入伪证据和真实矛盾确保不会为通过率放行。

责编局部修稿只能处理表达问题，不应作为章节编排、扩卷、UNKNOWN 或状态污染的修复替代。检查新 editorial 的异常处理是否将预算/UNKNOWN 变成普通 soft，纳入恢复回归；本轮未把它确定为此次中断根因。

## 6. 必须新增的验收场景

1. 单次启动授权三章，浏览器退出，不再逐章 POST /runs，三章全部接受。
2. 章完成后、后继请求落盘前后分别崩溃；重启只补一章，不丢章。
3. 双 Worker 同时处理完成事件；前台也点续写；仍只有一个权威后继 run。
4. 第一章终止失败：暂停/恢复/重试动作有效，不生成第二章掩盖缺口。
5. 预算暂停后刷新页面、授权继续，累计费用不清零，成功调用不重发。
6. 供应商返回未知时暂停对账，不把重启当免费重试机会。
7. 卷末待确认有真实决策入口；确认两次只建一卷；新卷首章可领取。
8. 目标卷数/章数已到，正确停止；自动模式不能越权扩展。
9. 16 个及更多被前章阻塞的任务存在时，其他作品仍可执行。
10. 用户改路径、产生旧分支/旧 attempt 后，调度只推进合法当前对象。
11. 旧调用键 checkpoint 跨版本恢复；新核验返工得到新键；已付费成功调用复用。
12. 三章事实、人物状态、承诺兑现具有正文证据；纠错旧章后按依赖范围重算，不混用旧事实。

真实模型验收分为三章功能验证、十章连续稳定性、跨卷旅程。每轮冻结预算与样本，保留全部失败和人工干预。报告分别统计：自主完成率、人工干预次数、可恢复停点、无任务空转时间、每千合格字成本、重复调用/扣费、连续性硬错误。有限样本成功不是长篇质量认证。

现有 R3 脚本保留为逐章诊断工具，但重命名或标注 supervised；新增验收入口必须只启动一次并观察 Worker。否则“脚本替系统续写”会继续掩盖产品缺口。

## 7. 上线和存量修复

先补可观测与幂等，再迁移数据。存量作品生成只读修复清单：RUNNING 无任务、RUNNING+TERMINAL_FAILED、已扩卷但 PENDING_DECISION、旧分支候选、旧调用键在途、终局待定。

对每类使用正式应用用例进行可重放修复，并留事件；不在脚本中直接改状态和清零账本。旧 auto_advance 不自动推断为无限连续授权：已有明确目标/授权时沿用，否则由用户选择连续范围。

回滚时停创建新的后继任务，允许已领取合法任务安全收口；保留账本、旧检查点读能力及已创建后继任务的身份。模块删减和进一步重构不应与这批连续创作修复捆绑发布。
