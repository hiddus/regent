# 858a 修复开发质量评估：代码、提示词与验收

日期：2026-09-19。对象：当前未提交工作树中的 858a 修复批次，重点覆盖 repair_locate、directing_script_loop、chapter_review、continuation、resume、调用身份兼容及 novel-web 接线。

## 结论

**有实质改进，但未达到可宣布修复完成或生产验收通过的质量。建议暂缓发布本批闭环能力。**

代码层已补上显式场景索引、修订票据、审核原结果留存、恢复阻塞原因、SQL 前章屏障和按 run_id 推进。但仍存在真实矛盾软化、无效定位默认首场、重复定位偏移、旧调用键兼容未落地，以及连续创作入口与并发事务缺口。

提示词从泛化“重写”进步到定点修订，但问题类型、证据用途和验收规则仍混在一起。当前不是简单的文案润色问题：程序把事实冲突的证据包装成“重复摘录”，再让模型遵循错误修订目标，可能产生看似听话但没有纠错的结果。

本评估不采用缺少标尺的百分制。代码正确性、提示契约一致性、产品闭环均判为“部分完成”；真实文学质量仍未认证。

## 发布前问题

### F1 · P1：真实知识矛盾仍可被关键词误判为 soft

位置：`directing_script_loop.py:194` 的 `_audit_cont_softable`；`scene_card.py:237` 的 `is_empty_state_discovery_false_positive`。

主函数虽然移除了原先宽泛词表，却继续调用旧误报辅助函数。该函数看到“入场状态”与“不知道”，或“缺少发现”，就返回 True。它没有接收入场事实、正文证据或状态来源，不能判断是否真的是空状态误报。

最小实测：将“入场状态明确他不知道密码；正文未获知密码却直接输入正确密码”作为 hard_fails，critical_missed 为空，`_audit_cont_softable` 返回 True。修满后该路径可放行真实矛盾。

修复要求：误报判断必须核对真实输入状态及证据；缺证据时保留硬失败。补上“非空已知状态 + 未获知知识却行动”的反例，不能仅测试普通关键词已不再匹配。

### F2 · P1：无效定位变成默认首场；REVIEW 缺定位也默认首场

位置：`repair_locate.py:325`，以及 `chapter_review.py:458` 附近。

`select_repair_target` 将任意非空 scene_ids 视为已定位。当 ID 不属于场景卡时，它最终回退 earliest=0，仍返回 locatable=True。模型定位在 `_begin_located_scene_repair` 中未先校验 ID、摘录归属和内容版本。输入不存在的 scene_id，实测返回 `True, s0, 0`。

REVIEW 的另一条路径将缺失的 failed_scene_index 转成 0；摘录也无法定位时，兼容助手接受这个伪定位。越界索引还会被夹到合法范围。旧的“默认末场”因而部分变成“默认首场”，并可能截断全部后续场。

修复要求：ID 必须属于当前场景集合，证据必须归属该版本；缺失和越界均明确停在不可局部定位。保留 None 的语义，不通过夹取或默认值制造位置。混合已定位与未定位问题也应完整留在票据中。

### F3 · P1：无长段落的场景导致重复定位偏移

位置：`repair_locate.py:108` 的 `_paragraph_scene_map`。

重复检测只统计长度至少 32 字的段落，但映射器为没有这类段落的场景额外插入一个虚拟槽。两套索引因此不一致。

实测：场景 s0 只有短句，s1/s2 各包含同一长段；期望定位 s1/s2，实际得到 s0/s1。即使摘录另行匹配出正确场景，虚假 s0 仍可能被合并并成为最早修订目标。

修复要求：检测与映射共用一次分段及位置记录，不插入虚拟槽；覆盖空场、短段、混合长短段及跨场重复。

### F4 · P1：连续创作授权没有产品调用入口

位置：`works_continuation.py:64` 的 `set_continuation_policy` 及其调用链。

检索当前 core/src 与 novel-web，找到策略 setter 定义和读取路径，未找到产品 API/服务调用 setter 的入口。策略默认关闭，测试通过直接调用 setter 开启，普通用户无法通过正常流程启用该能力。

这属于接线未完成，不应仅归类为“待线上验证”。此外 volume_scope、budget_grant_note 目前只是存储字段，ensure_next_run 没有消费它们来约束运行，不能据此声称卷范围和预算授权已落实。

修复要求：提供有身份校验、范围校验和版本控制的启停入口；明确目标章数、卷范围及费用边界，并从该入口做一次启动三章验收。避免通过直接改数据库启用来替代产品出口。

### F5 · P1：后继章创建缺少并发幂等事务处理

位置：`works_continuation.py:128–198`；`works_runtime.py:59–62`。

ensure_next_run 先查后插，没有锁作品推进记录，也没有冲突后读取已有任务的处理。双 Worker 同时补偿可能均看到后继不存在，然后插入相同 work/branch/chapter/attempt。数据库唯一约束会阻止重复行，但失败方 flush 会使当前事务失效。

补偿调用方捕获 Exception 后继续用同一 session 查询，却没有保存点回滚或事务重建，后续可能继续抛事务失效异常。此项为静态事务路径风险，本轮未做真实 PostgreSQL 并发复现。

修复要求：锁内复核或原子冲突处理；用保存点隔离预期冲突，返回已有后继。测试必须使用真实事务和两个连接，顺序调用或 fake session 不能证明并发幂等。

### F6 · P1：旧运行的调用键兼容仅有开关，没有迁移接线

位置：`directing_calls.py:73`。

读取的是 `production.call_key_version`，缺失时默认 2。旧检查点本来没有该字段，因此会带上 vrep0，无法保持旧格式。本轮检索只找到新运行在 generation_context 根部写入 2，未找到旧运行写入 1 或根字段传入 production 的迁移路径。

实测旧式 production 缺省字段时输出包含 `:vrep0:`。现有测试手工设置 version=1 能通过，只证明格式分支可用，不能证明升级后的旧任务会自动走该分支。

影响：既有成功逻辑调用可能不再命中，存在重复生成/计费或恢复冲突风险；本轮未证明线上已经发生重复收费。

修复要求：根据持久化协议身份明确旧格式，统一字段存放位置并完成迁移；用升级前检查点和已成功调用记录验证复用，而非只验证字符串格式。

### F7 · P1：事实修订被误写成去重任务

位置：`repair_locate.py:204、238`；`scene_card.py:320` 的执笔 system prompt。

所有 evidence_quotes 都被写成“必须删除或改写以下重复摘录”，并进入 must_remove_quotes；所有有摘录的问题都生成“摘录不得再重复出现”的 verify_rule，不区分 continuity 和 redundant。

实测：问题“钥匙应在小李手中”，证据“钥匙在小王手中”，expected_action=rewrite_scene，生成指令仍要求不得原样保留两处。执笔 system 又规定 must_remove_quotes 在本场至多保留一处。原有错误只出现一次，照这个约束原样保留也符合字面要求。

修复要求：分开 evidence_quotes（证明问题）、forbidden_claims（必须消除的错误断言）、required_state_refs（已核正确状态）、duplicate_pairs（重复位置）。非重复问题不得套去重模板；验收事实变化，而非检查证据句出现次数。

### F8 · P2：恢复 API 返回 blocker，但前端忽略并切换为恢复状态

位置：`apps/novel-web/src/App.tsx:750`。

后端现可用 HTTP 200 返回 resume_blocked 的 WorkResumeOut。前端 togglePause 仍忽略响应内容，直接 setPaused(!paused)，没有展示 blocker_code/detail/recommended_actions。API 的诚实状态没有形成用户可见闭环，恢复被阻塞时界面仍可能表现为恢复成功。

修复要求：根据服务端实际 state 和 blocker 更新界面；阻塞时保留暂停/失败显示并提供实际可用动作。对 repair_from_checkpoint 等建议动作核对是否存在对应入口。

### F9 · P2：历史失败 attempt 会永久阻止自动后继章

位置：`works_continuation.py:103` 的 `_earlier_in_flight`。

屏障统计所有更早章的 TERMINAL_FAILED，没有选每章权威 attempt。若同一章旧 attempt 失败、后续 regenerate 已 CANONIZED，但旧失败记录保留，屏障仍返回非零，阻止下一章创建。

这是与“保留失败证据”直接冲突的逻辑。修复应判断每章权威有效版本是否已接受，而不是删除历史失败。增加“attempt1 失败 + attempt2 成功 + 自动下一章”的真实数据库夹具。

## Prompt 质量专项评价

| 维度 | 已有改进 | 尚未解决 |
|---|---|---|
| 角色职责 | 编剧、执笔、场记、核验有分工；执笔明确输出完整本场 | 创作目标、事实约束、去重修订仍共用部分模板 |
| 修订范围 | 明确局部修订、保留正确节拍、不从零重写 | F7 将事实纠错导向去重；400 字截断可能截掉最后的实际错误说明 |
| 输入充分性 | VALIDATE 提供场景 ID 与 purpose，鼓励逐字摘录 | REVIEW 要求分场索引，但 payload 只有整章、前章、节点、canon，没有实际分场边界；模型只能推测 |
| 契约一致性 | repair_ticket 传入 scene_id、动作、证据 | system 写 expected_action 单数，payload 是 expected_actions 列表；尚无明确处理多个动作及冲突优先级的协议 |
| 证据使用 | beat_evidence 要求可在正文原样找到 | 定位引用与 hash 未统一由程序验证；模型填写 ID 不能被直接当可信映射 |
| 审核边界 | 明确真实事实矛盾不能 soft | F1 的程序降级推翻了 prompt 的严格要求；增加“必须”字样无法修正 |
| 质量评估 | 历史存在人工阅读对照 | 本批缺真实模型的修订成功率、审核误报率与盲评证据 |

建议统一提示契约：先说明当前任务及目标场；提供已核入口事实与正文版本；列出每项问题的证据、目标变化、禁止变化；明确输出 schema；程序按同一问题 ID 验收。信息缺失时返回无法判断，不猜场次或正确事实。

提示词验收应分三层：请求 payload 检查（字段和上下文齐全）、固定响应/失败夹具的程序行为测试、预算受控的真实模型对照。前两层通过不能证明第三层文学质量。

## 测试质量与完成度

现有测试有价值，尤其覆盖明确场定位、普通软化关键词、原审核保留、恢复返回及新旧键格式。518 项通过记录应保留，但新增套件偏重 fake session 和预设模型响应。

一个具体例子：`test_ensure_next_run_idempotent_and_respects_target` 只验证达到目标后不开第四章，并没有创建后继或模拟竞争，测试名不能作为“幂等性已经验证”的证据。

缺失的高价值覆盖为：

1. 无效/缺失/越界位置与混合可定位问题；短场后的跨场重复。
2. 真实非空入场事实下的知识冲突，确保任何辅助函数都不能误放。
3. 事实纠错 prompt 的输入输出语义，而非仅字段是否存在。
4. 旧检查点升级并复用旧成功调用。
5. 两个真实数据库连接竞争创建后继、失败事务恢复。
6. 历史失败保留后再生成成功，自动衔接下一章。
7. 从真实授权 API 开启连续创作；恢复失败时前端正确显示 blocker。

## 建议处理顺序

先修 F1/F2/F3/F7，确保不会放错、定位错、修错；随后完成 F6 的升级兼容。在宣称连续创作可用前，解决 F4/F5/F9 及 F8 的产品显示问题。

完成对应反例回归后，再做 PostgreSQL 并发与产品入口三章。最后使用冻结输入和预算的真实模型样本，分别统计事实修复率、误拦/误放、全部失败成本和人工阅读评价。无需为这轮修复扩大导演架构或追加无条件重试。

开发计划应将“代码已加入”“离线行为已验证”“产品入口已闭环”“真实模型质量已验证”分开标注；当前不能将本批概括为仅剩部署验收。
