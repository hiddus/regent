## 0. 决策摘要

Regent 保留正式执行中的边跑边修原则，但正式执行不得先于边界确认和可行性分析。每个 Goal 采用四段式治理：

1. **逐轮边界确认**：Goal 发布后保持 `DRAFT`，系统分轮确认目标价值、验收、范围、依赖、权限、预算和止损；
2. **可行性判定与锁定**：形成可审阅的 FeasibilityReport；只有结论为 `FEASIBLE` 且用户确认后，Goal 才能 `FROZEN` 并进入正式执行；
3. **运行中持续修正**：正式执行中把新证据和用户纠偏持续写回同一 Goal；实质改变边界时退回可行性闸门；
4. **硬预算止损**：分析与正式执行分别受硬预算约束，达到上限即停，不允许静默超额或同策略盲重试。

本决策取代“预算可以花掉，只要最终落经验”这一过宽读法。经验沉淀是必要条件，不是超预算的授权。

## 1. 逐轮边界确认

目标发布只创建 `DRAFT`，不得自动锁定或启动正式 Worker。确认采用多轮对话，每轮只处理一个主题、复述已确认内容并指出仍未确认内容；用户必须有机会修订或否决。建议顺序为：

1. **价值与责任人**：目标服务谁、解决什么问题、不做的损失、Goal Owner；
2. **结果与验收**：最小交付物、成功指标、护栏、基线、截止期及“不算完成”的条件；
3. **范围**：明确包含项、不包含项、优先级、允许简化及不得改变的约束；
4. **依赖与环境**：现有系统、数据可得性/质量、外部依赖、技术限制及负责人；
5. **权限与风险**：只读/写入、外部触达、资金、敏感数据、合规、审批和绝对禁止项；
6. **资源与止损**：分析预算、正式执行预算、Token/金额/墙钟/并发上限、最大损失、暂停/停止条件；
7. **候选路径确认**：拟采用路径、主要未知、替代方案和最低成本验证方式。

不得用一次总括性“是否确认”替代上述逐轮确认。允许合并用户已主动提供且无歧义的主题，但必须逐项回显确认状态。追问本身受分析预算约束，禁止重复询问已确认事实。

## 2. 可行性判定与 Goal 锁定

边界确认完成后，产品与技术视角共同形成 `FeasibilityReport`，至少包含：价值成立性、范围完整性、技术路径、关键依赖、数据/权限可得性、风险可治理性、预算匹配度、最小验证证据、剩余未知及建议。

`feasibility_verdict` 只有三种：

- `FEASIBLE`：有证据支持目标在已确认范围、权限和预算内落地，且验收方式成立；
- `REVISION_REQUIRED`：存在可修复缺口，必须缩小范围、补依赖、调整预算或重新确认关键分叉；修订后重新评估；
- `NOT_FEASIBLE`：当前约束下无合理落地路径、价值不足、无法验收或风险不可治理；停止，不得正式执行。

Goal 仅在以下条件全部满足时锁定为 `FROZEN`：逐轮确认项完整；FeasibilityReport 有证据引用；verdict=`FEASIBLE`；分析预算未越界；Goal Owner 明确确认报告版本、Goal 内容与预算；Goal Charter/Permit 要求满足。锁定记录必须保存版本与内容哈希。

未通过闸门时只允许：预算内对话追问、只读资料/仓库检查、估算、设计推演，以及用户明确授权的隔离可行性实验。严格禁止业务编码、生成或修改 workspace 文件、启动正式 Worker、生产写入、对外触达和不可逆操作。可行性实验的产物必须隔离，不得被宣称为项目已开工。

## 3. 运行中持续修正

每个收费或高成本步骤必须能关联到 Goal、交付物、待验证假设或风险项之一。步骤完成后至少更新一项：交付进度、证据、未知状态、风险、用户决策或可复用经验。

运行中遵循：

1. 新证据推翻价值或可行性假设时，立即缩小范围、换验证路径或暂停，不因已经消耗预算而继续；
2. 同一策略在没有新证据、参数变化或错误修复时不得重复调用；
3. 用户纠偏写回同一 Goal；目标、验收、范围、数据、权限、预算或不可逆影响发生实质变化时，Goal 退回 `DRAFT`，重新确认并取得 `FEASIBLE` 判定后才能继续；
4. 不确定性影响关键分叉时给出 2–4 个有限选项；不把整套 PRD 编写责任转嫁给用户；
5. 失败必须留下结构化教训，但教训的长度与生成成本应和复用价值相称。

## 4. 硬预算止损

预算是执行权限，不是观察指标。必须同时约束：单步骤、单次 Run、Goal 累计和外部工具/第三方费用。任一硬上限命中时：

- 停止新的付费模型调用、工具调用和自动重试；
- 保存已完成产物、证据、成本、失败原因和最小恢复点；
- 向用户说明已获得的价值、尚缺证据和继续所需的新增预算或范围调整；
- 只有 Goal Owner 明确增加预算或修订范围后才能继续。

以下行为视为无价值消耗并应被阻止或计入质量失败：无决策用途的全仓重复读取、角色间重复转述、无新证据的同策略重试、未验收的大段生成、预算耗尽后的隐藏续跑，以及用更多 Agent/Token 代替明确责任与验证。

## 5. 产品判定与状态

状态主路径为：`DRAFT → BOUNDARY_CONFIRMING → FEASIBILITY_REVIEW → FROZEN → EXECUTING`。`REVISION_REQUIRED` 返回 `BOUNDARY_CONFIRMING`；`NOT_FEASIBLE` 或分析预算耗尽进入 `STOPPED`。正式执行中的实质边界变化返回 `DRAFT`。

## 6. 验收

- Goal 发布后至少经过多轮主题确认，界面可见已确认、待确认与修订内容；
- 未取得 `FEASIBLE` 且未经 Goal Owner 确认前，没有业务编码、workspace 写入或正式 Worker 启动；
- FeasibilityReport 能回答价值、验收、路径、依赖、权限、风险、预算和剩余未知；
- Goal 锁定保存确认人、报告版本与内容哈希；
- 每次正式实质执行前可回答“本步服务哪个结果、如何验收、最多花多少、何时停”；
- 无新证据的重复策略不能继续消耗预算；
- 任一硬预算上限命中后不再发生付费续跑；
- 暂停时保留可审阅产物、成本对账、失败教训和最小恢复点；
- Goal Charter 与外部效应 Permit 不因本决策降级。
