## 二、失败项逐条研判

### 1. 获得第一页内容与进入修炼阶段被合并判断

核验要求陆沉成为“持有《残生录》第一页、右眼能看见禁制暗纹的淬体境初窥者”。所引正文为：“那些血色小字已经渗进他掌心，纸页上只剩一片灰白。”

这一摘录不能单独证明“未获得内容”：文字入掌可能是玄幻叙事中的传承方式，也可能只是未解释的异象。应分别核验内容是否被获得、能力是否出现、修炼状态是否改变，不能用纸页变空直接否定全部成果。另一方面，摘录确实不能证明已进入淬体阶段；如果全文也没有身体变化或能力证据，这部分属于真实缺失。

### 2. 面临信任选择与完成信任选择可能混淆

核验同时提出“未决定是否信任阿枝”以及“未体现必须决定是否信任阿枝，而信任意味着分享秘密”。正文引文是让阿枝明天留下最底下那勺粥。

“必须决定”可能描述章末困境，“已经决定”才是完成状态。若剧本设计的是悬念，要求本章解决选择就会改变戏剧目标；若剧本明确要求作出决定，则只约定留粥确实未必足够。必须回看原始剧本及该句所属字段，不能只凭核验转述裁定。

两个信任问题存在重叠，应合并到同一验收项，避免同一缺失产生多条修订任务。

### 3. 阿枝察觉异常不等于陆沉意识到泄密

摘录写阿枝看陆沉的嘴、看他发抖的手。这能支持她注意到异常，却不自动支持陆沉已意识到秘密暴露。若剧本要求主角认知发生变化，正文需要视角内的反应或行为证据。此项是合理的待核验缺口，不能直接当成吹毛求疵。

## 三、代码与 prompt 机制

### A. 前端分场允许遗漏，末端验收硬拦截

`core/src/regent/novel/domain/scene_card.py:744` 的 `structural_plan_issues` 将 must_land、转折、代价、终点未覆盖过滤为软问题；`directing_script_loop.py:826` 保存 `compile_soft_issues` 后可继续。

而整章核验接收完整 selected_script，并据此判断关键节拍与代价。这形成确定存在的机制风险：计划阶段未落实的要求，可能直到正文写完才成为硬失败。需要取得本次 compile_soft_issues 才能证明该风险在本次实际触发。

不建议简单恢复所有字面匹配为硬门禁。应把真正必须兑现的状态变化分配到具体场次；语义覆盖可以接受改写，但不能没有责任场次和正文证据。

### B. 自由文本同时承载结果、认知、困境和悬念

`script_protocol.py:145` 的 end_change 是自由字符串；选择器又要求 must_land_beats 写戏效果/读者感受。它们缺少明确的验收类型，容易把“让读者感到危险”“主角意识到危险”“主角完成应对”混在一起。

当前核验 prompt（`directing_script_loop.py:1212` 附近）要求兑现剧本、引用正文并定位，但没有明确规定：接受语义等价兑现；区分已完成结果与待解决困境；不得新增境界名称必须原文出现等要求；重复问题应合并。这使核验模型拥有过大的解释空间。

建议为关键要求标注“本章必须完成 / 本章必须意识到 / 本章只需建立困境 / 可选表现”，附最小可观察证据和对应场次。保留文学表达自由，限制验收规则自由漂移。

### C. 修订存在上限，但本地证据不能说明每次修了什么

当前代码 `directing_script_loop.py:1342–1386` 用 chapter_validate_repairs 控制整章核验后的分场修订；计数小于 2 且有 scene_texts 时进入定位修订，否则报本次同类错误。

若服务端运行的是相同代码，该错误与修订次数达到上限或缺少分场文本相容。尚不能断言具体是哪条分支。`creative_repairs=0` 是另一计数，不能据此声称没有执行过定点修订。fault_taxonomy 为空同样不能证明创作没有问题。

应提取每轮问题、定位场次、修订指令、正文差异、剩余问题，判断是定位错误、未落实指令、改动被覆盖，还是验收标准变化。仅增加重试次数无法回答这些问题。

### D. 失败状态没有一致呈现

同一份 API 证据中，章节已终止失败，而作品/页面仍显示运行与写作。该问题会让使用者误以为仍在生成，并使试跑总结缺少明确失败原因。它是可独立确认的状态展示问题，不是正文失败的起因。

## 四、对架构、prompt、模型责任的判断

| 维度 | 判断 |
| --- | --- |
| 架构 | 多阶段验收要求未形成统一、可追踪的约束，存在确定风险；不足以据此推翻全部架构 |
| Prompt | 终点、困境、认知和语义等价的判断边界不够明确；本次信任选择及传承内容争议与此高度相关 |
| 生成模型 | 可能遗漏主角认知、境界变化等要求，但目前仅有核验摘录，不能判定能力上限 |
| 核验模型 | 有过度字面化和重复报告的嫌疑，尚不能认定全部误报 |
| 工程实现 | 修订过程证据不足，且失败状态投影不一致；前次代码检查通过不代表产品目标完成 |

## 五、处置与复验标准

1. 对齐本次部署版本，取出选定剧本、分场卡、正文和逐轮修订记录；先判每个失败项是真是假。
2. 将复合终点拆分为独立验收项，区分既成结果与章末悬念；写作与核验共用同一清单。
3. 开写前保证硬要求有具体场次承接；终点尚未落实时优先补计划，不等整章写完。
4. 定点修订按验收项去重并保留前后证据，明确未解决原因；不要为了通过而统一降级硬错误。
5. 修正终止失败时的页面状态及失败原因呈现。
6. 以本案例进行真实端到端复验，确认第一章关键状态、认知与悬念均按约定兑现，再验证连续三章入库；另对固定样本人工标注核验真假，测误报与漏报。需要评估模型时，固定输入、规则和预算再做对照，避免把不同 prompt 的结果当模型能力比较。
