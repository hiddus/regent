开场 · WHY THIS TALK

为什么拿它当教材？

📘
它的「说明书」写得极好
目标、原则、验收标准、架构图，样样齐全，挑不出逻辑毛病。很多人第一次看都会觉得：这项目稳了。
💥
但它从头到尾没真正跑起来
文档里想得明明白白的能力，落到代码里，核心那一条「自己把事办成」的闭环，始终没打通。
一句话总结这次教训
定义和架构不是重点——让一件事端到端跑通、并且能验证真跑通了，才是 Agent 的命根子。
讲师注：本课不教你怎么「造」一个 Regent，而是借它的失败，弄清搭 Agent / 多 Agent 的基本功。文档代号（G1-G12、MA-0~6 等）留在本课最后「可跳过」区，备课时对照用。

CHAPTER 01

它到底想干什么？

先把目标讲成人话。看懂「它想成为什么」，才明白后来为什么摔得这么惨。
01
第一章 · 定义

一句话说清 Regent

文档里写了一长串公式，翻译成人话就是：
你给它一个目标 + 一堆不许碰的红线，它自己想办法把事办成，并且交活儿之前，先自己验证「确实办成了」。
输入是什么
一个目标（如「把这本书读完好，答出 10 道题」）+ 约束（如「不能乱花钱、不能瞎发消息」）。
它做什么
自己拆任务、自己派活、自己执行、卡住了自己救、做完自己查。
输出是什么
一个「带证据的交付」——不是嘴上说做完，而是拿得出验证过的成果。
讲师注：文档原公式 Regent(G,C,V,R_t,S_t)=… 表达的就是上面这句话。听课小伙伴不必记符号，记住「目标 + 红线 → 自己办成 + 自己验证」即可。
第一章 · 澄清误会

它不像什么（先排三个误会）

❌ 以为它是…
  • 又一个聊天机器人：只陪你聊，不真去办事。
  • 一个写好的自动脚本：流程写死，换个任务就废。
  • 一个只会答问题的搜索引擎：给答案，但不落地。
✅ 它其实是…
  • 会动手的同事：接了活，自己去把结果做出来。
  • 能随机应变的执行者：任务变了，它重新想办法。
  • 交活前自查的人：做完先验证，再交给你。
关键区分：聊天机器人「说」；Regent 要「做 + 验证做没做成」。后来失败，恰恰是因为它停在「说」这层，没走到「做 + 验证」。
第一章 · 心智模型

它像什么？——一个不会累的项目经理

🧠 接活就拆
老板丢一句「把网站做出来」，它自己拆成：搭框架、写页面、联数据库、自测……
📋 派工有条
每个子任务发一张「开工条」，限时、超时作废，避免有人干到天荒地老。
🔧 卡住自救
某步报错或超时，它不躺平，换条路再试，或老实报告「这步我真救不回来」。
✅ 交差前自证
说「做完了」之前，先跑一遍验证：真读完了？真答对了？拿得出证据才交付。
记住这个比喻就够了：Regent = 一个不会累、会自己想办法、且交活前先自查的项目经理。后面所有架构，都是为了让这个「项目经理」靠谱。
第一章 · 不变的原则

它给自己定的硬规矩（节选）

文档里列了十条「不可违背的原则」。挑最要命的四条讲——这四条，后来全被自己破了。

A
能不找人就不找人。 默认自己闭环，实在不行再打扰你。→ 后来却把「等你确认」当成了常态，主循环卡死。
B
交付前必须自己验证。 不能嘴上说做完。→ 后来很多「完成」其实是没验过的。
C
当时的原则：多 Agent 不是默认选项（成稿时原文：先证明单人能干，才考虑加人）。→ 后来架构先复杂了，单人闭环反而没跑通。
已被定义 3.0 修订（2026-08-10）：现行不变原则第 6 条是「智能体团队是产品形态，成员与拓扑可以自由演化，不以事前净收益证明限制探索」；单人先稳只是投入顺序建议，不再是加人的准入条件。真正的门禁落在扩大现实生产权限上。
D
每一步都得有迹可循。 做了什么、为什么，留证据。→ 后来「验证结果」常常没留痕，等于没发生。
讲师注：原则原文编号为不变原则 1–10。此处只取与失败最相关的四条，避免信息过载。C 条是本课唯一被后续定义修订过的一条，讲的时候要把「当时口径」和「现行口径」分开说，否则学员会带走一条已经撤回的规则。
第一章 · 成功标准

怎么才算「成功」？

文档定的「北极星指标」，说人话就是：
每办成一件真事，花了多少真成本（钱、时间、外部动作）。越低越好。
「真事」是什么意思
不是「我跑了流程」，而是「目标确实达成、且验证过」。读没读完书，以答对题为准，不以「我打开了文件」为准。
八条护栏是什么
比如：不能乱花钱、不能重复发消息、不能卡死不报、不能假装完成…… 护栏就是「再聪明也不能越的线」。
讲师注：北极星原文为 CostPerVerifiedSuccess（每验证成功一次的成本）。护栏原文 8 条，此处概括，细节见讲师速查。
第一章 · 毕业标准

它给自己定的 12 道「毕业考题」

文档里叫 P1 毕业矩阵，共 12 关。说人话：要算「成人」，得先过这 12 道真活儿考验。

① 真读完一本书
不是打开文件，是读透并答对题。
② 真跑通一个网站
从空目录到能访问，不止写代码。
③ 真修好一个 Bug
改完要自测通过，不是改完就交。
④ 卡住能自救
超时/报错后有明确出路，不悬空。
⑤ 不乱花不乱发
对外动作受控、可查、可回滚。
⑥ 交差带证据
每件事交付都附验证结果。
⑦ 不重复造轮子
能复用就复用，不瞎写。
⑧ 真多任务不乱
同时多个目标不互相踩。
⑨ 失败了能复盘
出错留下教训，下次不犯。
⑩ 人能随时接手
关键时刻人介入，它让位。
⑪ 边界内行事
不越护栏，不偷偷扩权。
⑫ 说人话汇报
进展用大白话讲，不是吐日志。
讲师注：即原文档 G1–G12。列在此让你感受「标准定得多实在」——可惜后来一关都没真验证通过。下一章看它怎么设计的。

第二章 · 关键机制

什么是「派工许可证」？

🎫 一张限时开工条
每派一个活，发一张条子：写明「干啥、限时多久、干完找谁销账」。像工地派工单。
⏰ 超时自动作废
条子到点没销账，就作废，活儿回到待派状态——防止有人干到天荒地老没人管。
🔁 可恢复，不悬空
作废不是「丢了」，而是有去处：重派、或老实报告「这步救不回」。
💡 后来怎么破的
条子发出去，活儿卡住，却没人销账、也没作废——任务就「悬在半空」，系统以为还在干，实际早死了。
一句话：许可证是「防卡死」的保险丝。保险丝没接好，后面全崩。
讲师注：即原 ExecutionPermit 生命周期（issued→active→expired/revoked→settled）。字段细节见速查。
第二章 · 关键机制

它怎么跟「外部世界」打交道？

原则：凡是会花钱、会发消息、会改外部数据的动作——
先记账，再执行；记完才算数，出事能查、能撤。
❌ 危险做法
  • 想到就直接发消息、直接扣钱。
  • 出错了不知道发过没，重复发。
  • 外部系统回没回，全靠猜。
✅ 该有的做法
  • 动作先写进「账本」，标「待执行」。
  • 执行完回写「已执行 / 失败」。
  • 失败可重试、可回滚，全程留痕。
讲师注：即原 ExternalOperation + Outbox 事件链。这是「不乱花不乱发」护栏的落地机制。后来这条链常常断了——动作发了，账本没记，等于裸奔。
第二章 · 关键机制

怎么保证它「不撒谎」？

📌 事实只有一个源头
「任务做到哪了」只有一份权威记录，谁改都留痕，不各说各话。
🏆 交付要有「奖杯」
说「做完了」，得附上验证产物（如测试通过截图、答对题的记录），否则不算数。
💡 后来怎么破的
「完成」常常只是代码跑完了流程，奖杯（验证产物）没留——系统信了，其实没真成。
🔍 查证官独立
验证的人和干活的分开，不让「自己说自己行」。
这层（查证层）是 Regent 的灵魂：没有它，「完成」只是自我感觉良好。
讲师注：即原 Artifact / 事实源（Source of Truth）边界。后来「奖杯」缺失，是「交付前必须自己验证」原则被破的直接证据。

第三章 · 演变 · 多 Agent

它想的多 Agent 方案（人话）

文档里规划了一支「分工团队」：有人专拆目标，有人专写代码，有人专测试…… 听起来很专业。

🧭 规划员
只管把大目标拆小、排顺序。
🔧 执行员
只管真去干活（写码/读文件）。
🧪 测试员
只管验证「真做成了没」。
❌ 栽在哪儿
  • 团队还没组好，先定了「要多 Agent」。
  • 单人（单 Agent）那条最基础的闭环，没先跑通。
  • 结果：分工图很美，没人真把活干完。
✅ 正确顺序
  • 先让一个人能把一件事端到端办成。
  • 证明单人靠谱了，再把活拆给多人。
  • 多 Agent 是「加速」，不是「遮丑」。
讲师注：即原 MA-0~6 多 Agent 计划。原则原文也写了「多 Agent 非默认」，但落地时顺序反了——这正是根因 C/D 的缩影。
第三章 · 演变 · 质量闸门

它想的质量闸门（人话）

🚪 毕业前先过小考
每个能力在「宣布能用」前，得先过一组真实验收：真读、真写、真修、真验。
📊 验收只看行为
不看出勤（跑没跑流程），看结果（目标达成没、验证过没）。
💡 后来怎么破的
闸门画了，但「小考」常常没真考——用「流程跑完」冒充「验收通过」。
🔁 带回归保护
每改一次，自动重跑小考，防止「越改越退」。
闸门的意义：让「我以为行」变成「证明确实行」。后来闸门失守，退化成摆设。
讲师注：即原 GQ-0~5 单 Agent 质量基线。与第 10 页「12 道毕业考题」同源——都是「先验证再宣布」的思想，可惜都没真落地。
第三章 · 演变 · 对话交付

它想的「对话式交付」（人话）

理想：你像跟一个新同事交代活儿一样——
说目标、给红线、看进展、卡住时它来问你，而不是吐一堆日志让你自己猜。
想要的样子
「我在做 X，卡在 Y，需要你确认 Z」——人话、带上下文、能决策。
实际的样子
要么沉默不动（等你确认却没提醒），要么甩原始素材（一堆文件，没说要你干嘛）。
讲师注：即原 CD-0~12 对话式交付规范。失败点：交互「没超时、没上下文、没决策建议」——和根因 A（主循环未闭合）直接相关。

第四章 · 根因总览

五大根因（一张图记住）

A 主循环没闭合
核心「办成+验证」从未端到端跑通
→
B 把流程当能力
流程跑完 ≠ 事真做成
→
C 工程卫生缺失
改了不敢验、错了查不出
→
D 优先级倒置
先搞复杂架构，基础没落地
→

写文档/画图，代替真把活干完

五条不是并列，而是一条压一条：因为主循环没闭合（A），才用流程假装能力（B），才没精力搞卫生（C），才先炫架构（D），才用元工作自我安慰（E）。

下一页起，每条配 ❌当时 / ✅该怎样。也可按需逐条讨论。
第四章 · 根因 A

A · 主循环没闭合

❌ 当时怎么做
  • 「拆目标→派活→执行→验证→交付」这条主链，每一段都写了，却从没串起来真跑过一次。
  • 永远在补某一环，没让整条链端到端流动。
  • 结果：每段都「差不多」，合起来「都没成」。
✅ 本来该怎样
  • 先拿最小一件事（如「真读完一篇短文档并答 1 题」）跑通整条链。
  • 链通了，再往里加能力；链不通，不加任何新东西。
  • 把「整链跑通」当成唯一进度指标。
一句话：先让一件事从头跑到尾，再去谈架构。这是 Regent 摔得最狠的一跤。
第四章 · 根因 B

B · 把「流程」当成了「能力」

❌ 当时怎么做
  • 代码走到了「生成完成」那一步，就记作「任务完成」。
  • 至于生成的东西对不对、能不能用，没人验。
  • 「跑完」被当成了「做成」。
✅ 本来该怎样
  • 完成 = 目标达成 + 验证通过，二者缺一不可。
  • 验证要真跑：读没读完，以答对题为准。
  • 验不过，就不算完成，回到干活环节。
流程是骨架，能力是血肉。只有骨架、没有血肉，站不起来。
第四章 · 根因 C

C · 工程卫生缺失

❌ 当时怎么做
  • 改了代码，没有自动小考回归，不知退没退步。
  • 失败码定义了 9 种，生产里一次没接住。
  • 一个没 tracked 的文件导致整个导入报错，藏了很久。
✅ 本来该怎样
  • 每次改动自动重跑验收小考，红就拦下。
  • 定义的每个失败处理，都要有真实触发路径。
  • 依赖、数据格式变更带迁移脚本，CI 里冒烟。
卫生不是琐事，是「改了不怕坏」的底气。没它，越改越心虚。
第四章 · 根因 D

D · 优先级倒置

❌ 当时怎么做
  • 单人闭环还没跑通，就先设计多 Agent 分工、评测协议。
  • 把「架构看起来高级」排在「先把一件事办成」前面。
  • 复杂度涨得比能力快。
✅ 本来该怎样
  • 投入顺序：单人跑通 → 状态机无悬停 → 验收只看行为 → 卫生/评测 → 再把重心移到多 Agent。
  • 任一层没稳，不要把投入重心押到下一层（这是重心建议，不是许可门禁）。
  • 多 Agent 是「加速」，不是「打地基」；沙箱里的多角色试验默认开放，门禁只落在生产默认与现实权限。
地基没打，楼越高越危险。
第四章 · 根因 E

E · 元工作替代了真工作

❌ 当时怎么做
  • 写文档、画架构图、定规范，占了大量精力。
  • 这些「关于做事的事」，代替了「真去把事做出来」。
  • 文档越完美，执行越苍白。
✅ 本来该怎样
  • 文档是「给别人看的地图」，不是「自我感动的勋章」。
  • 每份文档配一个可验证的落地动作，否则不写。
  • 用「真跑通」证明文档没错，而非用文档假装进展。
敲边鼓的本质：用「准备」逃避「交付」。

1
9 种失败码，生产里 0 次引用。 不是系统没失败，是失败全从缝里漏走了，没人接住——等于安全网是画的。

第五章 · 单 Agent 七步法

搭一个 Agent，七步走

1
定最小目标
2
画主循环
3
跑通一次
4
加状态机
5
立验证关
6
搞卫生
7
才谈多Agent
七步的核心纪律
多 Agent 是「加速」，不是「遮丑」。前 5 步没稳就靠分工去补，只会把混乱翻倍——这是投入顺序建议，不是准入条件：沙箱里的多角色试验随时可做，需要门禁的是把它变成生产默认、扩大现实权限。
下面两页把这七步拆开讲，配「❌别这样 / ✅要这样」。讲师注：不要说成「不许试多 Agent」——按定义 3.0 ATTRIBUTE_2/7，沙箱试验默认开放，七步法约束的是投入重心和生产晋级。
第五章 · 七步法详解（1/2）

第 1–4 步：先把一件事跑通

1
定最小目标：别一上来就「做整个平台」。选一件小得能验证的事，如「读这篇文档，答 1 题」。
2
画主循环：目标 → 拆解 → 执行 → 验证 → 交付。先画清楚这条链，别先画分支。
3
跑通一次：❌ 只写不跑。✅ 真端到端跑一遍，看到「交付 + 证据」才算数。
4
加状态机：❌ 状态能卡死、无出路。✅ 每个状态有去处，超时/出错都能恢复或漂亮地挂掉。
前四步的终点：一件真事，从头跑到尾，且你信它真成了。
第五章 · 七步法详解（2/2）

第 5–7 步：稳了再加速

5
立验证关：❌ 流程跑完=完成。✅ 达成 + 验证通过才算；验证要真跑，不比划。
6
搞卫生：❌ 改了不验、错了查不出。✅ 每次改动自动回归小考；失败处理都要有真触发路径；依赖变更带迁移。
7
才把重心移到多 Agent：❌ 单人没稳就指望分工来补。✅ 单人闭环跑通且稳，再把活拆给多个角色「加速」；沙箱里的多角色对照试验不必等这一步。
七步是一口气走完的「地基」，不是七份文档。每一步都用「真跑通」证明，不是用 PPT 证明。第 7 步排在最后是投入顺序，不是许可顺序。
第五章 · 多 Agent 原则

多 Agent 怎么搭？（原则）

① 单人先稳（投入顺序，非准入）
多 Agent 是加速，不是打地基。地基没稳，分工只会让混乱翻倍——但这是投入重心的建议；沙箱里的多角色试验默认可做。
② 按能力分，不按层分
谁擅长拆、谁擅长写、谁擅长验，让专长说话，别硬切层级。
③ 交接带证据
一个 Agent 交给另一个，附上「做到哪、证据是啥」，不靠口头「搞定了」。
④ 有总指挥
谁来判断「整体成了没」？得有一个角色兜底，不能各自为战。
⑤ 失败能收口
任一 Agent 卡死，系统能重派或上报，不悬空。
⑥ 评测冻结
「算成功」的标准先定死、先跑通单人版，再上多人，不临时改规则。
讲师注：对应原多 Agent 评测协议 + MA 计划的精神。此处只留原则，避免代号轰炸。
