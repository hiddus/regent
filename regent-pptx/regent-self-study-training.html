Part Ⅰ

先把三个层级拆开

一次执行、长期运行、组织协作，是三个不同问题。

Ⅰ
AgentLoop

AgentLoop 是一次“受约束的认知—行动闭环”

它回答：在一个任务、一个工作区和一份预算里，Agent 怎样把意图变成可验证产物？

理解目标Goal + acceptance
→
形成下一步plan / todo
→
调用工具read / edit / run
→
观察结果tool feedback
→
显式提交submit
→
验证与修复verify / repair / stop
可靠 Loop = 策略 + 工具边界 + 上下文管理 + 验证器 + 预算 + 明确终态
Regent

Regent 是 Loop 外面的“耐久控制面”

模型可以忘记，进程可以重启，但目标、授权、证据和责任不能丢。

交互与目标层自然语言 Goal、约束、成功标准、人工决策；负责“到底要什么”。
Regent 控制面状态机、调度、预算、权限、证据、审计、恢复；负责“何时、由谁、在什么边界内做”。
AgentLoop 执行面模型调用工具完成一次有界工作；负责“下一步具体怎么做”。
能力与运行环境模型、工具、技能、沙箱、构建与部署 Provider；负责“有什么手段可用”。
三者关系

AgentLoop 是发动机，Multi-Agent 是变速箱，Regent 是整车控制系统

Execution primitive

AgentLoop

一个 Agent 在一次 Run 内：思考、调用工具、观察、提交、验证、同轨迹修复。

优化目标：单次执行质量与成本。

⊂
Organization option

Multi-Agent

多个 Loop 按角色和依赖协作；增加并行、独立验证，也增加协调和冲突。

优化目标：组织净收益。

⊂
Durable control plane

Regent

从 Goal 到外部结果，选择组织、授予权限、记录状态、恢复运行、形成证据。

优化目标：目标达成的可治理性。

快速判断

不要问“能不能多 Agent”，先问“问题属于哪一层”

查清一个 API 行为

单次、低副作用、短上下文。

优先：单 AgentLoop

跨两天交付一个应用

要恢复、审批、预算、部署和外部验收。

需要：Regent 控制面

并行研究三个独立市场

分区清晰、合并规则明确、可独立验证。

候选：固定 Multi-Agent
Part Ⅱ

Regent：让自治变得可治理

它的核心不是“更聪明”，而是“在边界内持续交付”。

Ⅱ
产品定义

Regent 把自然语言目标变成可独立运行、可外部验证的结果

“在约束、资源、授权和治理边界内，形成当前最合适的最小人机组织，创建并运营可脱离 Core 的应用，并依据外部结果持续调整。”

输入不是 PRD 表单

GoalSpec 是系统解释的结果，不是用户先填完的作业。

组织不是产品身份

单 Agent、固定团队和人类参与都只是候选手段。

循环不是无限运行

成功、耗尽、不可恢复失败或取消，都必须形成有证据的终态。

架构边界

Kernel 不是 Agent：一个管“事实与权限”，一个管“局部求解”

Regent Core / 控制面

  • Goal、Work、Run 的权威状态
  • 调度、租约、Outbox 与耐久计时
  • Permit、人工任务、密钥与审计
  • Artifact、Evidence、Observation
  • 组织与能力注册、评测和晋级

Agent 不应拥有的权力

  • 凭对话内容直接改权威状态
  • 绕过授权执行外部副作用
  • 把自评或内部 smoke 当成功
  • 在生成时偷偷补造业务需求
  • 用无限重试掩盖不可恢复失败
事实架构

把“事实、证据、界面、模型建议”分开

层次它是什么能否直接驱动状态/副作用典型例子
事实源唯一可写权威，带版本和状态机可以，但须满足不变式Goal、Run、Permit、ExternalOperation、Outbox
Artifact / Evidence不可变、内容寻址、可审计提供依据，不单独授权代码快照、测试报告、观察记录、SBOM
投影为人显示，可从事实重建不可以对话时间线、进度页面、Agent 活动视图
模型输出概率性候选，必须校验不可以计划、假设、代码变更草案、路由建议
删除界面投影后，系统仍应能从事实源 + Artifact 重建完整叙事。

正确的闭环不是“生成完了”，而是“外部结果改变了下一轮”

模型自评、代码存在、页面能打开，只能说明“内部动作发生过”。
能力架构

缺能力时，顺序应该是“复用优先，构建最后”

1 复用已有认证能力
→
2 配置参数/权限适配
→
3 组合多能力编排
→
4 构建沙箱内新能力
→
5 请求人类授权/信息/决策

MCP 解决什么

工具发现、参数契约与调用语义。它是接口层，不是治理层。

Regent 仍必须解决什么

能力认证、Permit、预算、fencing、撤销、审计、失败恢复与证据归档。

可靠性骨架

长任务的基本功：不悬停、可重放、不重复副作用

Durable State

进程退出不等于任务消失；状态进入数据库并带版本。

Lease + Heartbeat

谁在执行必须可判定；失联后允许安全接管。

Outbox + DLQ

状态与事件同事务；毒事件有死信和修复路径。

Idempotency

外部调用有幂等键、fencing token 和对账机制。

任何非终态，都必须回答：谁会在什么时候，把它推进到哪里？
Part Ⅲ

架构如何演变，又如何失控

每一层复杂度都应该偿还一种已观察到的失败。

Ⅲ
演进时间轴

正确演进：先把“单条链路”做硬，再扩大组织自由度

脚本原型

Goal → LLM → 文件
证明可行性

P0 可靠内核

状态、权限、证据、恢复、预算

P1 单 Agent 闭环

生成、验证、部署、观察、修复

固定组织候选

明确角色、依赖、合并与验证协议

自适应组织

沙箱内默认可试；统计 Gate 只决定何时扩大现实生产权限

真实偏航：单 Agent 交付闭环还不稳定时，项目已经投入大量精力建设组织引擎、治理闸门和评测框架。
复杂度预算

新增组件前，先写清楚它要消灭哪一种失败

拟新增机制它应该偿还的故障必须观察的信号没有证据时
消息队列 / 事件总线数据库 Outbox 吞吐已成瓶颈排队时间、消费延迟、重放成本继续模块化单体
第二个 Agent可分区工作或独立验证明显受益成功率、延迟、成本、协调失败优化强单 Agent
新审批 Gate存在不可逆或高风险外部效应风险降低、等待时间、误拦截用策略自动化
新文档/新规范已有权威源无法表达关键决策冲突减少、执行可验证更新唯一权威源
演进洞察

复杂度增长得比交付能力快，架构就会从护栏变成阻力

↑

我们快速增加了

  • 组织编排与角色合同
  • 治理 Gate 和 DecisionRecord
  • 评测 Harness 与大量指标
  • 诊断、审计、修复计划
→

但用户侧交付没有同步增长

最小闭环、状态出口、事件消费、干净构建和真实验收仍然不稳。

架构成熟度 ≠ 组件数量；它等于在故障下仍能交付可验证结果的能力
Part Ⅳ

失败复盘：定义满分，执行敲边鼓

不是为了批判，而是为了识别 Agent 项目最危险的伪进展。

Ⅳ
2026-08-02 诊断快照

失败不是感受：用户进展、队列与终态同时发出红灯

32 天无用户侧有效进展
21GenerationRun 处于 PENDING
8FAILED 无法进入明确终态
4,400+核心执行编排器代码行数
工程信号：干净 checkout 曾因未入库模块直接 ImportError；失败经验数据因 schema 不兼容被静默过滤。
组织信号：多 Agent 与治理能力建设领先于强单 Agent 真实任务基线。
五个根因

看似是很多 Bug，本质是五种基本功缺口

A 单 Agent 闭环未闭合

没有稳定的 Goal → 进展 → 结果 → 终态。

B 控制流冒充能力

“代码路径存在”被当成“真实行为已通过”。

C 工程卫生欠账

提交、迁移、事件消费、背压和幂等不稳。

D 优先级倒置

先做高阶 graph，再补单 Agent 基本功。

E 元工作替代真工作

文档、审计与计划制造了严谨工作的幻觉。

共同结果

治理越来越完整，用户可验证产出却没有增加。

验收语义

“控制流已实现”是工程进度，不是能力证据

伪验收：证明东西“存在”

  • 类名、函数名或字符串能搜到
  • 开关和路由已经接线
  • Mock 单测覆盖了预期分支
  • 页面能打开、接口返回 200
  • Agent 自己说“任务完成”

真验收：证明结果“发生”

  • 冻结任务集端到端重复运行
  • 真实模型、工具、权限与总预算
  • 产物由独立验证器检查
  • 外部 Observation 对齐成功标准
  • 失败能进入明确、可解释终态
工程纪律

Agent 越不确定，底层工程就越要确定

版本控制

新模块、迁移与测试成套提交；干净环境必须能启动。

数据契约

字段演进带迁移与兼容读取；禁止静默丢失学习数据。

可观测性

区分排队、执行、等待、阻塞；记录主失败原因而非噪声。

故障注入

模拟超时、重复投递、worker 死亡、模型截断与权限拒绝。

“模型有随机性”不是降低测试标准的理由，而是增加不变式测试与统计实验的理由。
反指标

这些数字上涨，可能意味着系统更差

+Agent

Agent 数量

不是能力指标；更多成员可能只增加同步成本。

+Msg

消息与协作轮次

可能是角色不清、合并失败或隐式冲突。

+Ctx

上下文与 Token

可能是记忆边界不清、没有 Artifact 卸载。

更好的北极星：单位预算的可验证目标结果 + 终态率 + 恢复成功率
Part Ⅴ

正确搭建：先闭环，再组织

把每一个架构选择变成可证伪的假设。

Ⅴ
七级搭建路线

一个可靠 Agent 系统，应按这个顺序长出来

1 成功标准固定任务 + 外部结果
→
2 单 Loop工具、提交、验证、停止
→
3 耐久执行状态、租约、恢复、幂等
→
4 治理权限、Permit、审计
5 外部闭环Observation 驱动下一轮
→
6 组织实验沙箱内并行候选拓扑对照
→
7 条件晋级扩大现实权限时的统计 Gate + 回滚
出场规则：前一级未通过真实固定用例时，不扩大该能力的现实生产权限；沙箱内的研究、原型与组织试验默认开放（定义 3.0 ATTRIBUTE_7）。
最小 AgentLoop 合同

先做一个“失败也很清楚”的单 Agent

必须具备

  • Goal anchor 与成功标准每轮可见
  • 最小权限工具集与工作区边界
  • 计划 / todo 可持久化
  • 显式 submit，不把自然语言停机当完成
  • 独立验证器返回结构化 gaps

必须停止

  • 最大轮数、Token、时间和成本预算
  • 相同 gap 指纹重复出现
  • 权限不足或外部依赖不可恢复
  • 验证无改进且修复预算耗尽
  • 用户取消或更高优先级治理规则触发
Stop condition 是能力的一部分，不是失败后的补丁。
耐久会话

把“连续体验”与“连续进程”解耦

Dialogue

用户澄清、补充约束、查看进度。它是交互通道，不是执行状态机。

Project Session

持久绑定 Agent 身份、工作区授权、checkpoint 和 epoch，支持跨 Run 恢复。

Agent Run

一次有预算的执行轨迹。可成功、失败、耗尽或被替换。

不要为了“连续感”创造多个重叠 AgentLoop；执行仍应有唯一内核。
Multi-Agent 准入

多 Agent 只有在“可分、可合、可证”时才值得

任务特征倾向单 Agent倾向固定 Multi-Agent判断问题
依赖结构强顺序、频繁共享隐状态子任务弱耦合、可并行能否画出清晰 DAG？
验证需求同一执行者即可可靠验证需要独立审查或对抗性验证独立性带来多少风险下降？
单 Agent 基线成功率高、成本可控在特定任务族持续失败失败是否真由组织造成？
合并成本输出强耦合、冲突难解接口冻结、合并规则明确谁拥有最终决策权？
并行上限关键路径不可缩短墙钟时间可显著下降收益能否覆盖协调 Token？
固定组织模板

第一次 Multi-Agent，不要自适应：先把接口冻结

Coordinator

任务拆分者

冻结 DAG、分配预算、定义交付接口；不包办成员工作。

输出：任务合同 + 依赖 + 合并规则

→
Workers

并行执行者

在隔离工作区按合同产出 Artifact；禁止越权修改共享事实。

输出：可独立验证的增量

→
Independent verifier

独立验证者

按冻结成功标准验收，报告 gap；不得用多数投票代替事实。

输出：证据化 verdict

组织实验

Multi-Agent 的价值必须在同预算、盲评实验中被证明

冻结变量

  • 任务集与成功标准
  • 模型与采样配置
  • 工具、技能与权限
  • 总 Token / 时间 / 金钱预算
  • 外部依赖与运行环境
核心指标为什么必须看
外部任务成功率 + 95% CI判断提升是否超过随机波动
墙钟延迟与关键路径验证并行是否真省时间
总成本与协调 Token 占比识别“用更多资源买同样结果”
结构性失败率重复、角色越界、冲突、漏验证
恢复率与人工介入判断系统是否更可运营
净收益与护栏结果决定是否扩大现实生产权限，不决定能否进入候选：候选拓扑（含自适应拓扑）在沙箱内默认可试，事前不需要先证明有效（定义 3.0 ATTRIBUTE_2/5/6）。
上线策略

任何“更智能”的策略，都必须可观测、可回滚、可否决

Shadow

旁路运行，不产生外部副作用；先比较输出与成本。

Canary

稳定分桶，小流量真实任务；同时观察质量和故障漏斗。

Decision Gate

报告可复算，明确 GO / HOLD / STOP；默认不自动晋级。

Kill Switch

运行时立即回到安全基线；覆盖任何默认策略。

创新速度来自可逆性，不是来自取消护栏。
课堂练习 · 5 分钟

给实验室搭一个“数据清洗与报告 Agent”，你会怎么切层？

场景

输入 CSV 和自然语言要求；输出清洗后的数据、统计图和一页结论。数据含敏感字段，任务可能运行 40 分钟，失败后允许恢复。

问题 A

哪些责任属于 AgentLoop，哪些属于控制面？

问题 B

最小成功标准与外部证据是什么？

问题 C

现在需要 Multi-Agent 吗？什么证据会改变你的决定？

练习参考

一个克制的方案，通常比“全自动团队”更接近生产

第一版

  • 单 AgentLoop：读取、规划、生成转换脚本、运行、提交
  • 确定性验证：schema、缺失值、行数守恒、敏感字段扫描
  • 控制面：工作区隔离、预算、checkpoint、审计、恢复
  • 成功：固定数据集上结果正确，报告可追溯到清洗步骤

何时升级

  • 数据分片可独立并行，墙钟成为真实瓶颈
  • 需要独立统计审查，且能降低错误率
  • 单 Agent 在冻结任务集上持续暴露同类组织性缺陷
  • 接口、合并和冲突解决规则已经冻结

Takeaways

三个结论，带回你的下一个 Agent 项目

① 先做一个能稳定交付、失败有明确出口的 AgentLoop。
② 用 Regent 式控制面承载状态、权限、证据与恢复。
③ 把 Multi-Agent 当作待证明的组织策略，而不是默认答案。
