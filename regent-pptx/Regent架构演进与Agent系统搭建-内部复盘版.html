📖 定位 02
贯穿案例：云岭景区

经营目标不是“做一个系统”，而是持续把景区运营好

云岭景区年客流 300 万；索道、接驳、停车、商户、保洁、安保和应急共同运行。
旺季目标：平均入园等待低于 20 分钟，重大安全风险不增加，投诉下降，同时维持商户收入。Regent 跨天、跨季节感知变化，组织人和数字能力执行动作，并用真实结果修正策略。

感知

预约、闸机、热力、天气、停车、设备、交易、投诉。

行动

限流、接驳、排班、维护、广播、营销、应急和人工接管。

结果

等待、密度、安全、满意、投诉、收入和复游率。

📖 定位 03
运营目标不是单指标

Regent 必须在安全可行域内处理多目标权衡

安全底线

容量、雷雨、消防、设备和应急规则拥有否决权。

服务体验

等待时间、拥堵、投诉解决与信息透明度。

经营目标

票务、商户收入、人员效率、能源与维护成本。

长期韧性

设备健康、员工能力、供应商、季节策略与复盘记忆。

关键：不是给四个 Agent 各一个 KPI 后投票，而是由治理规则定义优先级、可行域、授权人和升级路径。
📖 定位 04
Regent 核心公式

每个时刻，都选择当前约束下业务效用最高的最小组织

Regent(G, C, V, Rt, St) = arg maxOt ∈ 𝒪 U(Ot | G, C, V, Rt, St)

输入：现在要解决什么

G 运营目标；C 预算、时效和业务约束；V 权限、安全、合规与责任规则。

依据：此刻真实世界怎样

Rt 可用的 Agent、Skills、工具、人力与设施；St 客流、设备、天气、事件和历史状态。

决策：由谁怎样行动

Ot 是最小可行人机组织；U 综合安全、体验、收入、成本、时延与人工负担。

云岭景区例子：雷雨导致索道停运后，最优组织可能从“单 Agent 调整接驳”变为“Agent + 值班经理 + 安保”；环境恢复后再缩回。Multi-Agent 只是 Ot 的一种候选。
📖 定位 05
持久运营闭环

一次 Run 结束，景区仍在营业

Regent 的持久性：保持受管实体、目标组合、运营状态、责任链和学习记忆连续；不是让一个 Agent 进程永远不退出。完整闭环（Sense → Diagnose → Decide → Organize → Act → Observe → Learn → Next shift）将在 Part Ⅱ 展开。
Part Ⅰ

先把一个 Agent 做完整

Context 决定它知道什么，Skills 决定它会怎样做，Loop 让能力在环境中持续生效。

Ⅰ
Agent 的能力内核

Agent 不是一个 Loop；Loop 只是它使用能力的运行机制

Context · 当前认知Goal、运营状态、历史证据、约束、对话与当前任务；决定 Agent 此刻看见什么。
Skills · 可复用能力领域方法、流程、检查清单、工具使用规则与经验；决定 Agent 遇到问题会怎样做。
Tools · 行动接口读取系统、分析数据、调用票务/排班/工单、写 Artifact；决定 Agent 能改变什么。
Loop · 执行机制观察 → 判断 → 行动 → 获取反馈 → 验证/修复/停止；让前三层在真实环境中工作。
Agent = Model + Context + Skills + Tools，在受约束 Loop 中运行
Agent 是 Regent 的核心

Regent 不替 Agent 思考；Regent 让 Agent 能长期、受控地承担运营责任

Agent 负责

  • 理解当前 Situation 与目标
  • 按 Skills 形成计划和候选动作
  • 调用工具、产生证据、验证结果
  • 遇到缺口时请求能力或人工支持

Regent 负责

  • 组装可信 Context，选择可用 Skills
  • 保存跨 Run、跨班次运营状态
  • 控制权限、预算、副作用和人工接管
  • 根据任务选择单 Agent 或其他组织
关系：没有强 Agent，Regent 只是一个空调度器；没有 Regent，Agent 只能完成一次次孤立任务。
正确的嵌套关系

Regent 以 Agent 为核心，并按任务选择组织方式

Regent Operations Plane围绕景区等受管实体，维护目标、状态、治理、证据、责任链和真实结果。
Organization Decision针对当前 Situation 选择最小可行组织；按 Situation 选择最小可行组织；沙箱可试多角色，扩大现实生产权限需证据。
Agent · 核心执行单元基于 Context 和 Skills 诊断、计划、行动与验证；每个成员都必须是完整 Agent。
Execution LoopAgent 内部的运行机制，不是与 Agent、Regent 并列的产品层。
Multi-Agent = Regent 某次任务的 Organization Plan；不是 Regent 的同义词。沙箱内默认可试；扩大生产默认与现实权限才受净收益 Gate 约束。
快速判断

先判断需要什么 Agent 能力，再判断需要几个人

一次设备告警

装载设备诊断 Context 与维修 Skill，由一个 Agent 分析和核验。

强单 Agent

整个黄金周运营

Regent 持续组装状态、触发 Agent、治理动作并跨班次复盘。

Regent + Agent

重大综合事件

只有客流、安全、设备需要并行研判时，才形成临时多 Agent 组织。

Part Ⅱ

Regent：让自治变得可治理

它的核心不是“更聪明”，而是“在边界内持续交付”。

Ⅱ
产品定义

Regent 是现实运营对象的持久自治运营系统

围绕一个长期存在的受管实体，在安全、合规、资源和责任边界内持续感知环境，解释并平衡目标，形成最合适的人机组织，采取行动，并依据真实运营结果调整策略、能力和组织。
公式的产品含义：Regent 持续重复“读取 G/C/V/Rt/St → 选择 Ot → 观察结果 → 更新状态”，而不是交付一次答案后退出。

对象长期存在

景区、商超和城市不会随着一次 Run 结束。

行动改变现实

排班、票务、维护、调度和应急产生真实后果。

软件只是手段

看板、小程序、模型或工具仅在运营需要时创建。

架构边界

Kernel 不是 Agent：一个管“事实与权限”，一个管“局部求解”

Regent Core / 控制面

  • Goal、Work、Run 的权威状态
  • 调度、租约、Outbox 与耐久计时
  • Permit、人工任务、密钥与审计
  • Artifact、Evidence、Observation
  • 组织与能力注册、评测和晋级

Agent 不应拥有的权力

  • 凭对话内容直接改权威状态
  • 绕过授权执行外部副作用
  • 把自评或内部 smoke 当成功
  • 在生成时偷偷补造业务需求
  • 用无限重试掩盖不可恢复异常
事实架构

把“事实、证据、界面、模型建议”分开

层次它是什么能否直接驱动状态/副作用典型例子
事实源唯一可写权威，带版本和状态机可以，但须满足不变式Goal、Run、Permit、ExternalOperation、Outbox
Artifact / Evidence不可变、内容寻址、可审计提供依据，不单独授权代码快照、测试报告、观察记录、SBOM
投影为人显示，可从事实重建不可以对话时间线、进度页面、Agent 活动视图
模型输出概率性候选，必须校验不可以计划、假设、代码变更草案、路由建议
删除界面投影后，系统仍应能从事实源 + Artifact 重建完整叙事。

MCP 解决什么

工具发现、参数契约与调用语义。它是接口层，不是治理层。

Regent 仍必须解决什么

能力认证、Permit、预算、fencing、撤销、审计、故障恢复与证据归档。

可靠性骨架

长任务的基本功：不悬停、可重放、不重复副作用

Durable State

进程退出不等于任务消失；状态进入数据库并带版本。

Lease + Heartbeat

谁在执行必须可判定；失联后允许安全接管。

Outbox + DLQ

状态与事件同事务；毒事件有死信和修复路径。

Idempotency

外部调用有幂等键、fencing token 和对账机制。

任何非终态，都必须回答：谁会在什么时候，把它推进到哪里？

复杂度预算

新增组件前，先写清楚它要解决哪一种问题

拟新增机制它应该偿还的故障必须观察的信号没有证据时
消息队列 / 事件总线数据库 Outbox 吞吐已成瓶颈排队时间、消费延迟、重放成本继续模块化单体
第二个 Agent可分区工作或独立验证明显受益成功率、延迟、成本、协调问题优化强单 Agent
新审批 Gate存在不可逆或高风险外部效应风险降低、等待时间、误拦截用策略自动化
新文档/新规范已有权威源无法表达关键决策冲突减少、执行可验证更新唯一权威源

六个阶段性根因

不只是系统没跑稳，连验证问题本身也选错了

A 单 Agent 闭环未闭合

没有稳定的 Goal → 进展 → 结果 → 终态。

B 控制流冒充能力

“代码路径存在”被当成“真实行为已通过”。

C 工程卫生欠账

提交、迁移、事件消费、背压和幂等不稳。

D 优先级倒置

先做高阶 graph，再补单 Agent 基本功。

E 元工作替代真工作

文档、审计与计划制造了严谨工作的幻觉。

F 验证场景错位

目标是景区等大组织的持久运营，却长期用线上调研网站验证；没有真实场景，也没有足够领域 Skills。

验收语义

“控制流已实现”是工程进度，不是能力证据

伪验收：证明东西“存在”

  • 类名、函数名或字符串能搜到
  • 开关和路由已经接线
  • Mock 单测覆盖了预期分支
  • 页面能打开、接口返回 200
  • Agent 自己说“任务完成”

真验收：证明结果“发生”

  • 冻结任务集端到端重复运行
  • 真实模型、工具、权限与总预算
  • 产物由独立验证器检查
  • 外部 Observation 对齐成功标准
  • 异常能进入明确、可解释终态
工程纪律

Agent 越不确定，底层工程就越要确定

版本控制

新模块、迁移与测试成套提交；干净环境必须能启动。

数据契约

字段演进带迁移与兼容读取；禁止静默丢失学习数据。

可观测性

区分排队、执行、等待、阻塞；记录主要异常原因而非噪声。

故障注入

模拟超时、重复投递、worker 死亡、模型截断与权限拒绝。

“模型有随机性”不是降低测试标准的理由，而是增加不变式测试与统计实验的理由。
反指标

这些数字上涨，可能意味着系统更差

+Agent

Agent 数量

不是能力指标；更多成员可能只增加同步成本。

+Msg

消息与协作轮次

可能是角色不清、合并困难或隐式冲突。

+Ctx

上下文与 Token

可能是记忆边界不清、没有 Artifact 卸载。

更好的北极星：单位预算的可验证目标结果 + 终态率 + 恢复成功率
Part Ⅴ

正确搭建：把单 Agent 做硬，同时让组织自由试

Context、Skills、工具和验证决定能力下限；净收益只决定何时把某种组织形态扩大为生产默认，不决定它能否被尝试。

完整 Agent 合同

先确保 Agent“看得对、会得够、做得稳”

Context Contract

  • Goal 与优先级
  • 当前运营状态和时间
  • 可信证据与数据质量
  • 权限、预算和停止条件

Skill Contract

  • 何时加载该 Skill
  • 领域步骤与检查清单
  • 所需工具和输入契约
  • 异常分类与升级方法

Execution Contract

  • 显式计划与下一动作
  • 副作用授权和幂等
  • 独立验证与结构化 gaps
  • 预算耗尽或同类异常重复即停止
耐久会话

把“连续体验”与“连续进程”解耦

Dialogue

用户澄清、补充约束、查看进度。它是交互通道，不是执行状态机。

Project Session

持久绑定 Agent 身份、工作区授权、checkpoint 和 epoch，支持跨 Run 恢复。

Agent Run

一次有预算的执行轨迹。可成功、未达成、耗尽或被替换。

不要为了“连续感”创造多个重叠 AgentLoop；执行仍应有唯一内核。
一种可选组织方式：Multi-Agent

生产默认偏置：Context/边界确需拆分时再增员；沙箱试验不在此限

任务特征保持单 Agent（生产默认偏置）考虑 Multi-Agent（含沙箱并行试）必须回答
Context一个 Agent 可保持完整一致专业域上下文互相污染或过大拆分后怎样共享权威事实？
Skills可按需加载多个 Skills需要独立专业责任和权限为什么不能用 Skill 动态加载？
依赖强顺序、共享隐状态子任务弱耦合、可并行合并接口是否冻结？
验证确定性验证已足够必须有独立审查或对抗验证独立性带来多少风险下降？
口径（定义 3.0）：上表是投入/生产默认启发式，不是探索准入。沙箱内组织试验默认开放；扩大现实生产权限才需对照证据。

上线策略

任何“更智能”的策略，都必须可观测、可回滚、可否决

Shadow

旁路运行，不产生外部副作用；先比较输出与成本。

Canary

稳定分桶，小流量真实任务；同时观察质量和故障漏斗。

Decision Gate

报告可复算，明确 GO / HOLD / STOP；默认不自动晋级。

Kill Switch

运行时立即回到安全基线；覆盖任何默认策略。

创新速度来自可逆性，不是来自取消护栏。
现场推演 · 5 分钟

国庆首日上午，景区出现三组冲突信号

场景

预约量比预测高 18%；雷雨将在 50 分钟后到达；山下商户希望继续引流。北门等待 42 分钟，索道正常，停车场接近饱和。

问题 A

哪些信号进入 Operational State？哪些规则必须是确定性不变式？

问题 B

需要哪些人、Agent 和现场系统组成最小组织？

问题 C

哪些动作可自动执行，哪些必须人工批准？如何验证处置有效？

练习参考

先建立安全可行域，再在其中优化体验和收入

最小组织

  • 客流 Agent：预测拥堵并提出分流
  • 安全策略：雷雨与容量规则拥有否决权
  • 值班长：批准停票、封区和跨部门调度
  • 现场系统：票务、广播、接驳、停车和排班

处置与验证

  • 自动提示错峰与停车余量，准备避雨区域
  • 值班长批准分时限流与增加接驳
  • 观察 15/30 分钟队列、密度、退款和投诉
  • 雷雨提前或密度越线时升级应急组织
目标不是“策略已发送”，而是拥堵真实下降、游客得到安置且安全风险未增加。

Takeaways

四个结论，带回你的下一个 Regent 项目

① Context 决定 Agent 看见什么，Skills 决定 Agent 会怎样做。
② Agent 是 Regent 的核心执行单元，Loop 是 Agent 内部的运行机制。
③ Regent 让 Agent 围绕现实对象跨 Run、跨班次持续运营。
④ Multi-Agent 只是 Regent 按任务选择的一种组织方式；生产默认是最小组织，沙箱内的组织演化默认开放。

把单 Agent 做硬，同时让组织在沙箱里自由演化
这次复盘真正的目的

Regent 还没有完成，需要更多人一起把它做成

目前暴露的是验证路径、Skills 供给和工程优先级的问题；这些问题需要通过真实场景、更多 Skills 和可复现实验逐步解决。

贡献真实场景

带来景区、商超、城市运营中的目标、约束、数据、角色和实际问题案例，让验证回到现实。

贡献领域 Skills

把客流、安全、设备、排班、供应链、应急等专业方法沉淀为 Agent 可加载、可评测的能力。

贡献开源工程

共同建设 Agent 内核、持久状态、治理、评测、适配器、文档和可复现实验。

我们邀请的不是围观者，而是共同定义问题、提供能力并验证结果的建设者。 Regent 的下一步，应从真实组织、真实 Skills 和真实结果开始。
