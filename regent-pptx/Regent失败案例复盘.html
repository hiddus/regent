1.1 · 公式化定义（PRD §0.1）

Regent 到底是什么？一句话 + 一个公式

Regent 接收人的自然语言 Goal，在明确的约束、资源、授权和治理边界内，自主解释目标，发现并补齐能力，形成当前最合适的最小人机组织，创建并运营可脱离 Core 独立运行的应用，并依据可验证的外部结果持续调整计划、能力和组织，直至目标达成、资源耗尽、不可恢复失败或被 Goal Owner 取消。
# 形式化：在 G/C/V/R_t/S_t 下寻找最优组织 O_t*
Regent(G, C, V, R_t, S_t) = arg max_{O_t ∈ 𝒪_Regent} U(O_t | G, C, V, R_t, S_t)

约束：
  C(O_t) ≤ 0          满足所有约束
  V(O_t) = True       符合治理与合规要求
  R_t(O_t) ≥ R_min    资源可用且不低于阈值
  S_{t+1} = Transition(S_t, O_t)   状态随执行不断演进
  lim GoalAchieved(S_t, G) = True   持续迭代直至目标达成
产品身份（PRD §0.1 原话）：“Regent 的产品身份不是「更强的单一 Agent」，而是管理 Agent 组织在约束与治理下自治运行的目标操作系统。”
第一章 · 定义与目标4 / 50
1.2 · 不可分割的恒定属性（复盘当时的 PRD §0.2，已被定义 3.0 取代）

当时的七条“不可分割”的恒定属性

  1. 1 Goal 驱动：唯一必需的用户输入是自然语言 Goal；GoalSpec 是解释结果，不是用户必须预先完成的需求。
  2. 2 边界内自治：自治始终受约束、资源、授权、治理和人工接管约束。
  3. 3 能力可演进：能发现能力缺口，并按 复用→配置→组合→构建→请求人类 的顺序补齐。
  4. 4 组织为执行手段：根据目标形成最小人机组织；单 Agent、固定团队、多 Agent 都是候选实现。
  5. 5 独立 App 是目标成果：生成的 App 拥有独立源码、依赖、数据、测试、部署，可脱离 Core 运行。
  6. 6 外部结果闭环：依据可验证的外部 Evidence 与 Observation 调整，不是生成者自评或内部 smoke。
  7. 7 明确终止：必须在成功、耗尽、失败或取消时形成有证据的终态。
这 7 条每一条都是“基本功”。后文会看到：项目不是没写它们，而是写好之后，没把每一条真正跑通。
口径更新（2026-08-10，定义 3.0）：现行 PRD §0.2 是九条，不再是这七条——目标定方向不定路径 / 探索默认开放 / 在实践中进化 / 团队是生命组织 / 证据用于学习（非许可）/ 资源自治 / 边界落在现实影响上 / 自由但不脱离现实 / 长期连续开放演化。变化最大的是原第 7 条「明确终止」：3.0 的 ATTRIBUTE_7 是「边界落在现实影响上」，语义完全不同。本页保留当时七条用于复盘，引用现行规格请看 docs/definitions/REGENT-DEFINITION-3.0.txt。
第一章 · 定义与目标5 / 50
1.3 · 不变原则（PRD §0.3）

十条不变原则——工程的“宪法”

  1. 1 现实接触、探索开放、持续学习、自主组织；失败关闭只适用于越权或不可逆现实影响。
  2. 2 Generated App 与 Core 分离；业务模型不反向固化进内核。
  3. 3 PostgreSQL + Outbox + 不可变 Artifact + Permit + UNKNOWN 对账。
  4. 4 内部 Smoke 不得满足产品价值 Gate。
  5. 5 Provider 不得注入缺失的业务功能。
  1. 6 智能体团队是产品形态；成员与拓扑可以自由演化。系统记录成本和结果并促进自然选择，不以事前净收益证明限制探索。
  2. 7 投票不能替代机器验证或真实 Observation。
  3. 8 团队可以自评、互评和继续实验；不可逆生产发布必须满足对应现实权限，并保留独立验证或人类接管通道。
  4. 9 禁止用源码字符串、类名存在或伪 Observation 代替行为验收。
  5. 10 变更门禁：定义以规范源为准；修改则新建定义 ID，禁止原地修改。
失败伏笔：原则 4、6、8、9 在后续实现中被反复突破——内部 smoke 充 Gate、多 Agent 默认化、生成者自评价、用源码字符串断言代替行为验收。这是“定义很好、落地很歪”的典型。
第一章 · 定义与目标6 / 50
1.4 · 产品边界（PRD §0.4）

Core 与 Apps 的边界

# 仓库边界（PRD §0.4 原文）
regent/
├─ core/   # 通用自治组织运行内核（G/C/V/R/S/O 的通用实现）
└─ apps/   # Regent 创建和运营的独立应用（目标成果）
  • Core 只表达目标、能力、组织、工作、执行、证据、策略和资源。
  • 每个 App 拥有独立源码、依赖、数据、测试与部署，可以脱离 Core 运行。
  • 具体内容类型、订阅方式和业务指标不得成为 Core 领域对象。
为什么这条重要：“内核不掺业务”是 Agent 系统能复用的前提。一旦把具体 App 的业务模型塞进 Core，内核就腐化成某个产品的专属胶水，再多 Agent 也救不回来。

1.5 · 北极星与护栏（PRD §8）

唯一北极星指标 + 八条不可抵消的护栏

# 北极星（PRD §8.1）
CostPerVerifiedSuccess
 = (模型成本 + 工具成本 + 基础设施成本 + 人工成本 + 失败恢复成本)
   / 独立验证成功的 Goal 数
窗口：滚动 28 天 UTC；分母 ≥10 个 VerifiedSuccess，否则 INSUFFICIENT_EVIDENCE
决策：连续 2 窗 北极星 > 基线×1.20 或任一护栏红 → STOP 投资评审
护栏红线
核心任务完成率< 70%
证据不足率> 30%
端到端 P95 延迟> 4h
人工介入分钟 / VerifiedSuccess> 120 min
重复副作用 / 未对账 UNKNOWN / 安全违规 / 内部流量误入决策> 0 立即停
护栏“不可被收益抵消”——这是度量体系的设计哲学，也是失败项目最该记住的一句话。
第一章 · 定义与目标8 / 50
1.6 · P0 核心能力（PRD §5.1）

P0：可靠、受治理的目标执行内核（10 条）

  1. 保存原始 Goal，生成版本化 GoalSpec，区分显式约束、系统推断和未知项。
  2. 持久化 Goal / Work / Run / Artifact / Evidence / HumanTask / Audit，进程重启后恢复。
  3. 从 Goal 与计划推导能力需求，区分能力、权限、资源、信息缺口和普通失败。
  4. 通过 复用 / 配置 / 组合 / 构建 / 请求人类 补齐能力。
  5. 根据能力覆盖组建最小组织，并能收缩、替换和解散。
  6. 在 apps/<app-id> 创建、构建和测试独立 App。
  7. 使用外部 Observation 和 Evidence 评价进展并重规划。
  8. 所有副作用行动经过策略判断和一次性 ExecutionPermit。
  9. 人工输入与审批使用独立 HumanTask，等待期间不占 Worker。
  10. 支持暂停、恢复、取消、预算限制、无进展停止和完整审计。
P0 完成定义（§5.3）：5 条必须同时满足，整体交付。其中第 2 条“仅凭普通 Goal 形成可解释的最小组织，补齐至少一个能力缺口，并通过 EVT_PARSER_GAP”是单 Agent 闭环跑通的核心判据。

1.9 · 多 Agent 评测协议（PRD §10）

“多 Agent 是需要被证明的策略，不是产品目标”

旧 PRD §10.1 原话（已被定义 3.0 修订）：多 Agent 是需要被证明的执行策略，不是产品目标。必须先以同一任务、模型、工具、权限和总预算运行强单 Agent champion，再决定是否允许固定模板或自适应组织进入候选。
现行口径（定义 3.0 ATTRIBUTE_2/4/6）：强单 Agent 只是对照基线，不是候选前置。候选拓扑在沙箱内默认可试；同预算冻结对比决定的是何时扩大现实生产权限或晋级默认策略。

冻结对比要求（任何候选组织都必须报告）

维度冻结要求
模型 / Prompt / 技能 / 工具 / 权限集合与版本哈希一致（除组织形态差异）
Token总 Token 与缓存 Token 分列
人工分钟计入净收益
口径pass@1 / pass@k 预先定义
coordination_token_share≥20% 为工程告警线（非自动失败线）
error_amplification_factor / dispatch_entropy故障注入与派工分布熵时间序列
旧 §10.1 初始裁剪规则（现仅作生产默认建议，不再限制候选）：单 Agent 基线成功率 >45% 时不默认建议多 Agent；强顺序依赖任务默认单 Agent；“中心化编排 + 独立验证”优先用于可分解且需独立验证的工作。沙箱内提出任意拓扑候选不受本规则约束。

2.5 · Goal 状态机（Plan §2 / Tech §7）

Goal 状态机——第一套，也是最核心的一套

ACTIVE ↔ PAUSED；ACTIVE/WAITING_HUMAN/BLOCKED → 四种终态。resume 只接受 PAUSED；终态不重开，改则新建 Goal 引原。
EXHAUSTED 铁律：只能由 Exhaustion Evaluator 提议 + 确定性规则确认；证据不足时进 BLOCKED，不能进 EXHAUSTED。这正是后文“交付缺口悬停、无出路的死胡同”的反面教材。

2.6 · Work 状态机（Plan §4）

Work 状态机——逻辑工作单元

PLANNED → READY → RUNNING → EVALUATING → ACCEPTED
             ↘ WAITING_HUMAN          ↘ REJECTED → READY
             ↘ BLOCKED
RUNNING → UNKNOWN
任意非终态 → CANCELLED
  • ACCEPTED 终态，成果通过独立验收；REJECTED 可在修订后建新 Run。
  • UNKNOWN：外部副作用无法确认，必须先对账。
  • 后续 Observation 推翻已接受结果时，不重开 ACCEPTED Work，而是创建纠正 Work + Replan。
关系：Goal 1 ──* Work 1 ──* Run。一个 Work 可多 Run，但同一时刻最多一个活动 Run；重试/换执行方式必须新建 Run，历史不覆盖。

2.7 · Run 状态机（Plan §5）

Run 状态机——一次不可变尝试

CREATED → PERMIT_PENDING → QUEUED → RUNNING
RUNNING → EXECUTED | FAILED | UNKNOWN | CANCELLED
PERMIT_PENDING → DENIED | EXPIRED | CANCELLED
  • 所有终态均不可修改：EXECUTED（正常返回，不表示 Work 已验收）、FAILED、UNKNOWN、DENIED/EXPIRED/CANCELLED。
  • 同一 Work 同时最多一个活动 Run。
  • UNKNOWN 不得自动重试；Reconciler 必须用外部回执/幂等键/权威查询产生对账 Evidence，再建纠正 Work 或新 Run。
失败伏笔：“UNKNOWN 不得自动重试、必须走对账”是后文 pipeline 死锁的直接成因之一——当对账链路本身没接上时，Run 就永远卡在 UNKNOWN/FAILED_TERMINAL，无法标记终态。

4.2 · 五大根因

为什么“架子全、交付空”？

  1. A · 主闭环未闭合。单 Agent “解释→计划→执行→验证→重规划”从没端到端跑通；S2 的目标被 S4/S5/MA/GQ/CD 持续稀释。

  4. D · 优先级倒置。先做多 Agent / 对话体验 / canary 等“亮眼”层，拖着单 Agent 闭环这个地基不补。
  5. E · 元工作替代真工作。大量批次在“计划怎么计划”“评测怎么评测”，真实 Goal 从头到尾没被端到端交付过。

② 沙箱未真执行（CD-6 / §13.8）：N-3 族（entrypoint 吞命令、uid 写盘失败、路径静默挂空、DinD）使 docker 模式“尚未真执行”。CD-6 全绿前开 canary 只会得到无效或假绿数据。
③ M6 canary ≠ GQ-4（§13.7.3）：M6 曾开 5% agentic canary，现已 CLAMPED_PENDING_QUALIFICATION（canary off；watch HALTED；须先 Offline Qual）；代码默认已是 agentic（artifact-backed 为 fallback），但 GQ-4 DecisionRecord 仍 PENDING。用历史开窗营造“已晋级”的错觉，是优先级倒置的集中体现。
三处共同证明：“控制流已就绪”和“能力已交付”是两件事；把前者当后者汇报，就是失败被掩盖的机制。

5.1 · Agent 怎么搭（7 步法）

先让一件事端到端跑通

  1. 定义不可变闭环：GoalSpec → Work → Run → Evidence → 验收 → 重规划，状态机先画清（参照 §2.5–2.7）。
  2. 副作用受控：所有外部效应走 Permit + ExternalOperation 原子派发 + operation_key 幂等（§2.9–2.10）。
  3. 证据分级：只认外部 Observation / build-verification 满足 Gate；内部 smoke 永远不够（§2.12）。
  4. 失败有出路：UNKNOWN 必须走对账；BLOCKED 可恢复；EXHAUSTED 需证据；禁止“未达标”死胡同（§2.5–2.7）。
  5. 可恢复 & 幂等：Worker 崩溃后从持久状态续跑；重放不产生第二份输出（CSV/EVT 基线）。
  6. 数据契约带迁移：schema 变更必须迁移 + 兼容；禁止静默丢经验（F-2 教训）。
  7. 验收只看真行为：默认策略翻没翻、窗开没开、经验沉淀没——用行为判定，不靠控制流已就绪。
顺序即纪律：前 5 步是单 Agent 闭环地基；地基不稳时，不把投入重心压到多 Agent 生产扩权 / 对话体验 / canary——沙箱试验仍可做。
第五章 · 结论46 / 50
5.2 · 多 Agent 怎么搭

沙箱默认可试；扩大现实生产权限才需证据

原则（定义 3.0 / PRD §10 / Plan §12.5）

  • 沙箱内候选拓扑、角色创造与组织试验默认开放（ATTRIBUTE_2/4/6/7）
  • 认证 Hive（aar1_certified_hive）代码默认 on；可按 Goal force_single_agent / env 退出
  • 把某拓扑晋级为生产默认并扩大不可逆现实权限前，须同任务/模型/工具/权限/总预算对照与净收益证据
  • 强顺序局部任务可由单责任 Agent 连续完成；团队保留统筹与验收
  • 机器验证优先于 LLM-as-a-Judge；不靠 Prompt 替代状态机/验证

扩大生产权限前

  • 局部执行闭环与对照基线可观测（GQ-0~5 控制流 ≠ 能力已交付）
  • 跑 P2-4 冻结实验（MA-5），出 DecisionRecord
  • 报告 coordination_token_share / error_amplification / dispatch_entropy
  • 正净收益 → 才扩大固定模板 / 自适应组织的生产默认与现实权限
  • 每次派工可回放：派给谁、为什么、依据什么证据
反面教材：本项目把 MA-0~6、GQ-0~5、CD-0~12 的“控制流”当成“多 Agent 已具备”，却把投入重心压到生产扩权 / canary，而主闭环与 MAST 生产接线仍缺——顺序反了。
