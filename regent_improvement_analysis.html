角度五：证据与反馈闭环 — "依据可验证的外部结果调整"

Regent 永久定义属性 6 要求"依据可验证的外部 Evidence 与 Observation 调整计划、能力和组织"。以下是闭环健康度：

  • P0 — 外部证据源不可用：Worker 日志持续输出 httpx.ProxyError: 403 Forbidden，证据源 HTTP 请求被 Egress Proxy 拒绝。这阻断了采集"可验证外部结果"的通道，25 个 Gate 因此返回 INSUFFICIENT_EVIDENCE。
  • P0 — 28 个目标卡在 PREVIEW_SUCCEEDED 无后续：这些目标通过了 Build/Deploy/Preview/Smoke 测试，但因为证据不足（或修复前的 bug）没有被推进到 Gate→Converge。修复代码（_continue_or_advance_milestone）已部署但不会对历史事件生效，除非手动合成新事件。
  • P1 — Observation 多样性不足：Observation 表包含 is_bot 和 is_internal 字段（符合设计），但实际数据量和多样性有限。G7 要求 ≥3 条合格 Observation，其中需包含 product_rejection 类型。
  • P1 — REVISE→Discovery 闭环不完整：5 个 REVISE 决策已产生，但对应的新 Discovery 是否成功闭环不可查。需验证 REVISE 后的新 Hypothesis→Generation→Build→Preview→Gate 完整链路。
S6
角度六：系统稳定性 — 运行态一致性与恢复能力
  • P0 — Worker 空闲 + 0 PENDING ≠ 系统正常：当前 0 PENDING 事件、10 DEAD_LETTER、Worker 空闲的状态，不代表所有工作已完成。28 个 ACTIVE PREVIEW_SUCCEEDED 和 30 个 NULL-stage ACTIVE 目标都是"悬空"状态。需要定时探活机制将卡死的目标推进或标记为需要人工干预。
  • P0 — 64 个 RUNNING Run 泄露：Run 的 Lease 到期后未被正确收敛。Worker Lease 机制依赖定期心跳，但 Lease 过期后的清理逻辑缺失。应增加定时任务扫描超时 Run 并根据其 Permit 状态对账收敛。
  • P1 — 死信自动恢复：10 个死信中有 8 个是可自动重放的（如 GenerationRunRequested 语义错误），但当前死信重放需手动操作。应增加：死信分类器、自动重放策略配置和重放阈值。
  • P1 — Outbox 事件幂等投递：1588 条 DISPATCHED 事件说明 Outbox 投递量巨大，但无重复投递检测机制。Technical Spec §5 要求"Worker 崩溃后新 Worker 先对账，不得凭 Lease 到期直接重复副作用"。
  • P2 — 迁移链完整性：DB 唯一约束变更（uq_metric_bindings）通过手动 SQL 执行，Alembic 迁移通过 stamp 而非 upgrade 跳过重复列。需要清理迁移链，创建正式 migration 文件记录当前数据库完整 DDL。

总结：当前阶段的核心矛盾

Regent 目前处于 P1 实现中期。执行链的主要骨架已打通（Discovery→Requirements→Capability→Generation→Build→Preview→Gate→Converge），但存在三个结构性瓶颈：

  1. 证据闭环断裂：Egress Proxy 403 阻断外部 Evidence，导致 Gate 评估无法通过。没有真实 Observation，Regent 的"依据外部结果调整"定义属性无法兑现。
  2. 稳定态缺失：64 个 RUNNING 泄露 + 30 个 NULL-stage 目标 + 28 个 PREVIEW_SUCCEEDED 卡死 = 超过 60% 的 ACTIVE 目标处于非健康状态。系统缺乏自愈机制。
  3. 实验基础设施空白：P0 完成定义要求 A/B/C 对照实验形成产品决策，但冻结任务集、Eval Harness 和统计 Gate 均未就绪。

解决这三个瓶颈后，P1 Graduation 的 SYSTEM_GRADUATED 层可在 2-4 周内完成验证。PRODUCT_EVIDENCE_GRADUATED 层需要至少 1 个完整的拒绝→REVISE→新 Discovery 闭环，取决于真实用户参与度。
